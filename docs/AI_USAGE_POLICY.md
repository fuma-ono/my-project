# AI利用ポリシー(Claude Code / Claude API 使い分けルール)

作成日: 2026-09-15
関連: `AI_USAGE_AUDIT.md`(現状監査)、`AI_AUTOMATION_ARCHITECTURE.md`(改善アーキテクチャ)

---

## 1. 基本原則

**Claude Codeを常時稼働する実行エンジンとして扱わない。**

優先順位(上に行くほど「本当に必要か」を厳しく判断する):

```
通常コード(GitHub Actions / script)で解決
        ↓
軽量AI(Claude API、定型プロンプト)で解決
        ↓
Claude API(複雑な判断・生成)
        ↓
Claude Code(開発・監査・戦略・障害調査)
```

新しい自動化を作る際は、必ず**下から**ではなく**上から**検討する。「AIに考えさせれば楽」という理由だけでClaude Codeを使わない。

---

## 2. Claude CodeとClaude APIの役割分担

### Claude Codeが担当する領域
- 開発・設計・大規模なコード変更
- システム監査(本ドキュメント群のような)
- 原因不明の障害調査(トークン失効、ワークフロー失敗の根本原因分析など)
- 改善案の作成・アーキテクチャ設計
- 戦略判断(週次経営レビュー、事業方針の変更)
- 人間の承認が必要な意思決定
- 新しい自動化を組む際の一次実装(安定後はAPI化を検討)

### Claude APIが担当する領域(自動化からの呼び出し)
- 定型フォーマットへの入出力が明確な判断(reply/skip判断、短文生成、分類)
- プロンプトが固定化できる創作(投稿文生成、要約)
- 呼び出し元は**GitHub Actions等の通常コード**であり、Claude Code(対話セッション)を経由しない

### どちらも使わない領域(通常コード)
- データ取得・API呼び出し・ログ保存
- 集計・フィルタリング・重複排除・JSON変換
- 単純な条件分岐(閾値判定、ファイルの有無確認)
- 定期実行の起動そのもの(cronの信頼性問題は、対症療法としてAIに叩かせるのではなく、cron設定自体 or 外部スケジューラで解決する)

---

## 3. Claude Codeを起動する前の判定ルール

自動化システムからClaude Code相当のフルセッションを起動する前に、必ず通常コード側で以下を判定する:

```
if 問題なし:
    起動しない
if 単純な修正・定型判断で解決可能:
    Claude API または通常コードで処理する
if 複雑な判断・設計・原因不明の障害が必要:
    Claude Codeを起動する(必要な情報だけを渡す)
if 人間の承認が必要な変更:
    Claude Codeは提案(ドキュメント・diff)までとし、実行は承認後
```

**「常時監視」は禁止する。** 以下のパターンは原則改善対象とする:

```
悪い例: Claude Code → 定期起動 → 状態確認 → 問題なし → 終了 → また定期起動
良い例: 通常コード → 異常検知 → 異常時のみAI(API or Code)を起動
```

現状(2026-09-15時点)、Threads自動化の「確実に起動」系Routine・「トークン監視」Routineがこの悪い例に該当することが監査で判明している。改善方針は`AI_AUTOMATION_ARCHITECTURE.md`参照。

## 4. コンテキスト最小化ルール

Claude Code / Claude APIを呼び出す際は、以下を徹底する。

- プロジェクト全体やログ全文を毎回読み込ませない。**必要な情報だけを事前に通常コードで抽出・JSON化してから渡す。**
- 例(良い例): KPI分析なら「昨日のKPIをスクリプトで抽出→JSON化→Claudeへ渡す」。プロジェクト全体を読み込ませてから分析させない。
- 同じ質問・同じKPIに対して繰り返しAIに聞かない。判断結果は`analysis.json`のようにキャッシュし、入力データが変わらない限り再利用する。
- 長時間の同一セッション維持を避ける。CCR Routineの「定期的に同じセッションを叩き続ける」設計は、コンテキストの蓄積(過去の会話・大量のツール結果)を招きやすいため、**機械的な定期処理は独立したGitHub Actions実行に切り出し、セッションの外に出す**(本ポリシーの核心)。

---

## 5. 「1日1回のAI判断」を基本単位にする

- 常時AIを動かすのではなく、`定型処理(GitHub Actions)→KPI収集→AI分析(1日1回 or 異常時のみ)→アクション実行→ログ保存`という構造を基本形とする。
- 毎時間・数分おきの判断が必要な自動化(現状の2時間おきの返信判断など)は、**本当にその頻度が必要か**を再検討する。返信の即時性がビジネス上重要でなければ、判断頻度を落とす(例: 4時間おき→1日2回)ことも検討対象とする。

## 6. 安全装置(異常時の自動停止)

### 6-1. 既存の仕組み(実装済み)
- `automation_guard.py`: 投稿・返信が3回連続失敗したら自動的に一時停止(`MAX_CONSECUTIVE_FAILURES = 3`)。2026-09-14に「状態ファイルがGitHub Actions実行のたびに消えて機能していなかった」バグを修正済み。
- `check_token_health.py`: 同一障害の再通知を防ぐ`notified`フラグ(2026-09-15修正済み)。

### 6-2. 追加で導入すべき仕組み(提案値、要オーナー確認)

現状(移行前)のベースラインが約52回/日であることを踏まえ、**「正常運用でも起こりうる範囲」より明確に高い値**を閾値とし、誤検知を避けつつ暴走は確実に検知する:

| 閾値 | 提案値 | 根拠 |
|---|---|---|
| 1時間あたりCCR Routine起動(Claude Code)回数 | **> 15回で自動停止・通知** | 現状の最密集時間帯でも1時間に5回程度(2h/4hおきの複数Routineが重なる場合)。15回はその3倍で、明確な異常(無限ループ・誤設定)のみを検知する水準 |
| 1日あたりCCR Routine起動回数 | **> 100回で自動停止・通知** | 現状ベースライン約52回/日、P0対策後は約15回/日を想定。100回は現状の約2倍であり、「対策前の水準に戻ってしまった」ことも検知できる水準 |
| 同一エラーの連続発生 | **3回で停止**(既存の`automation_guard`を踏襲) | 実装済みロジックと整合させる |
| Claude API呼び出しの連続失敗 | **3回連続で当該自動化を一時停止・通知** | `automation_guard`と同じ設計思想をAPI呼び出し部分にも適用 |
| Claude APIレスポンス異常(パース不能・スキーマ不一致) | **1回で当該実行を安全側(skip/保留)に倒し、3回連続で停止** | 誤った投稿・返信を防ぐ最終防波堤 |

**注記**: 上記の閾値は現状のRoutine構成から逆算した提案であり、実際のプラン上のAPI/セッション利用上限(Anthropic側の契約内容)はこのセッションから直接確認できない。オーナー側で契約プランの利用上限を確認のうえ、最終的な閾値を調整することを推奨する。

## 7. AI利用量の可視化(今後の実装方針)

現状、「どの自動化がAI利用量を消費しているか」を定量的に把握する仕組みが存在しない(本監査が初の定量化)。以下の記録を残す設計を今後検討する。

### 7-1. 記録すべき項目(提案スキーマ)

```
date, workflow_or_routine, task, model, execution_count,
input_tokens, output_tokens, estimated_cost, success, failure_reason
```

### 7-2. 記録元
- **Claude API呼び出し**(P1・P2移行後): 呼び出しスクリプト内でAPIレスポンスの`usage`フィールド(input_tokens/output_tokens)をそのまま`threads-affiliate/ai-usage-log.jsonl`(または事業ごとの同等ファイル)に追記する。これは通常コードで完結し、追加のAI呼び出しは不要。
- **CCR Routine起動(Claude Code)**: Claude Code Remote側のセッション実行記録(`list_sessions`/`list_triggers`の`last_run`)を定期的に(例: 週次経営レビューの一部として)集計し、`docs/`配下にレポートとして残す運用とする。専用の常時ログ収集の仕組みを新設するのは過剰投資であり、既存のCCR管理APIから取得できる情報の定期集計で足りると判断する。

### 7-3. 目的
「気づかないうちにAI利用量を消費している」状態を無くすこと。派手なダッシュボードを新設することが目的ではなく、**月次〜週次で「今どの自動化が何回AIを起動しているか」を一覧できればよい**。

## 8. 新規自動化を追加する際のチェックリスト

新しい定期処理・自動化を追加する前に、以下を必ず自問する:

1. これは本当にAIの判断が必要か?(単純な条件分岐やAPI呼び出しで済まないか)
2. AIが必要な場合、Claude Codeのフル機能(bash/git/任意ファイルアクセス)が本当に必要か、Claude APIの1回呼び出しで足りないか?
3. 定期実行(cron)にする場合、その頻度は本当に必要か?(1日1回で足りないか)
4. 失敗時の上限(最大リトライ回数・クールダウン・同一エラー検知・自動停止・通知)を実装したか?
5. 6節の閾値に抵触した場合、誰が・どう気づくか(通知経路)を用意したか?

このチェックリストを満たさない自動化は、Claude Code(このセッション)によるレビューを経てから本番投入する。

## 9. 本ポリシーの見直し

- P0/P1(`AI_AUTOMATION_ARCHITECTURE.md`)の実装完了後、実際の起動回数の変化を計測し、6節の閾値を再調整する。
- 四半期に一度、または大きな自動化追加時に、本ドキュメント群(AUDIT/ARCHITECTURE/POLICY)を見直す。
