# threads-affiliate 運用方針の全面見直し(2026-09-09、オーナー指示)

## 位置づけ

`2026-09-08-genre-pivot.md`で決めた「モバイルバッテリー・電気ケトル・折りたたみ傘・電気毛布の4ジャンルに絞る」方針は、**この文書により上書き・撤回する**。オーナーから、特定ジャンルに絞る運用そのものをやめ、アカウントの位置づけを再定義する指示があった。旧方針の経緯・却下理由の記録としては残すが、今後の商品選定・KEYWORDSは本文書に従う。

## アカウントの再定義

「特定の商品を売るアカウント」ではなく、**「暮らしの中で、これ知ってたら便利だったと思える商品・サービスを発掘して紹介するアカウント」**として運用する。表示名「便利、見つけた。」はそのまま維持(`brand.md`)。

ジャンルは限定しない。以下を幅広く対象にする(順不同):

- 生活便利グッズ / キッチン用品 / 家電
- スマホ・PC周辺機器 / 旅行用品 / 車用品
- 防災用品 / 季節商品 / 美容・身だしなみ用品
- 収納・掃除用品 / AI・Webサービス / その他日常の「これ便利」

ただし無差別ではなく、**「誰かの困りごとを解決する便利なもの」を優先する**。

**注記(AI・Webサービスの扱い)**: 楽天・Amazonの商品検索APIは物販のみを対象としており、SaaS/Webサービスは検索対象にできない。`research.py`による自動調査は物販ジャンルに限定し、AI・Webサービス系のネタは別途手動でリサーチ・執筆する運用とする(自動化の対象外であることをここに明記)。

## 投稿頻度・時間

- 目標: **毎日1投稿、21:00頃**
- 将来像: 20:00頃ネタ選定→生成→品質/コンプライアンスチェック→21:00投稿、を完全自動化
- ~~Phase 1: 20:00頃に投稿案を自動生成し、オーナーが確認してから手動投稿~~ → **2026-09-09、オーナー指示によりPhase 1を経ずPhase 2(完全自動投稿)へ移行した**
- **Phase 2(現在)**: 毎日20:00 JSTにRoutineが投稿案を生成・commit・push、毎日21:00 JSTに`threads-publish.yml`(GitHub Actions)が`pending/`の下書きを自動投稿する。人間のレビューは入らないため、`publish.py`の`validate_pr_disclosure()`(PR表記の有無・位置チェック)がコード側の最後の安全弁になる

## アフィリエイト: 楽天+Amazonの2本柱

- 楽天: 従来通り`research.py`で自動調査
- Amazon: `amazon-links.md`で手動管理(PA-API自動化はAmazon側で180日以内に3件の成果が必要なため現状不可)。**2026-09-09、オーナーがアソシエイト承認済み(税務情報アンケートは支払い停止回避のため別途対応予定)であることを確認した**。`amazon-links.md`に実際のリンクが登録された商品から順にAmazonリンクを使用する(現状`amazon-links.md`はまだ空のため、リンクが登録されるまでは実質的に楽天のみで運用継続)
- 同一商品で両方のリンクが使える場合は、`amazon-links.md`に登録があればAmazon優先(実績作りのため、既存ルールを維持)

## 投稿構成(基本形)

「商品説明」ではなく、**悩み→気づき→商品→利用シーン→CTA**の順を基本にする。

```
【PR】(冒頭に配置。末尾に小さく書くだけの設計は禁止)
↓
「これ、毎日地味に困ってる人いない?」(悩み・あるある)
↓
「調べてたらこんなの見つけた」
↓
商品紹介
↓
「こういう場面で便利」(利用シーン)
↓
必要最低限の特徴(スペック→メリットに変換したもの)
↓
「気になる人は↓」(CTA)
```

スペックの羅列(「○○機能があります」「容量○○です」「レビュー○○です」)だけの広告文にはしない。

## 投稿パターン(4種、ローテーションまたはランダム。商品との相性を優先)

| 日本語名 | `post_type`値 | 型 |
|---|---|---|
| 共感型 | `empathy` | 「これ地味に困るよね」→解決策→便利商品 |
| 発見型 | `discovery` | 「こんなのあるの知らなかった」→商品発見→便利な理由 |
| 比較型 | `comparison` | 「○○なら、これとこれどっち?」→違い→おすすめする人 |
| まとめ型 | `summary` | 「知らないと損かもな便利グッズ5選」→複数商品紹介(代表1商品にリンクを絞る、リンク集にはしない) |

旧`post-template.md`の5パターン(共感投稿/発見投稿/比較投稿/商品紹介/まとめ投稿)はこの4パターンに統合する。「商品紹介」は独立パターンではなく、上記4パターンいずれの中でも使う共通の投稿構成(悩み→気づき→商品→シーン→CTA)として扱う。

## PR・広告表示(必須、システム側で検証)

- 広告であることを隠さない。**投稿の冒頭**に【PR】等、読者が広告と明確に認識できる表示を入れる(末尾に小さく書くだけは不可)
- `publish.py`に、アフィリエイトリンクを含む投稿の本文が【PR】等の表記で**始まっているか**を検証するバリデーションを実装し、表記漏れ・末尾のみの表記を検知したら投稿を中断する
- Amazonリンクを使う場合は、Amazonが指定するアソシエイト表記(例:「Amazonのアソシエイトとして、〇〇は適格販売により収入を得ています」等の必要文言)も別途掲載できるようにする(実際にAmazon運用を始める段階で文言を確定し反映する)

## 商品選定ロジック(11項目、単純な人気順にしない)

1. 日常の悩みを解決するか
2. 「知らなかった」と思わせられるか
3. Threadsで話題にしやすいか
4. 一目で便利さが伝わるか
5. 季節性があるか
6. SNSで紹介したときにクリックしたくなるか
7. 価格が購入しやすいか
8. レビュー・評価が十分か
9. アフィリエイト対象として利用可能か
10. 競合が多すぎないか
11. 投稿ネタとして継続的に展開できるか

「便利だけど知られていない」商品を優先する。`research.py`のスコアは需要・満足度・価格帯による一次フィルタに過ぎず、実際に書く1件はこの11項目も踏まえて選ぶ。

```json
{
  "post_id": "...",
  "published_at": "...",
  "text": "...",
  "affiliate_url": "...",
  "affiliate_platform": "rakuten",
  "product_name": "...",
  "category": "...",
  "post_type": "empathy",
  "views": null,
  "likes": null,
  "replies": null,
  "reposts": null,
  "quotes": null,
  "shares": null,
  "clicks": null,
  "last_metrics_at": null
}
```

**2026-09-09追記**: `check_insights.py`の実機確認により、Threads Media Insights APIで有効なmetricは`clicks, likes, quotes, replies, reposts, shares, views`の7つのみと判明した。`profile_visits`相当のmetricは投稿単位のInsightsには存在しないため、フィールド自体を廃止した。`clicks`はリンク・ハッシュタグ・メンション・メディアへのクリックを合算した値で、アフィリエイトリンク単体のクリック数ではない可能性がある点に注意。

`category`は商品ジャンル(例: "キッチン用品")、`post_type`は上記4パターンの英語値。旧スキーマの`category`(実際には投稿パターンを格納していた)は`post_type`に役割を移した。
