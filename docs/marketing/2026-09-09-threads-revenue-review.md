# threads-affiliate 売上最大化レビュー(2026-09-09)

オーナー依頼による、Threadsアフィリエイト自動化システムの「売上最大化」観点での厳格レビュー。コードは変更せず、実装(コード・データ・GitHub Actions実行履歴)を実際に調査した結果。

---

## 0. 調査で分かった実態(前提)

- **GitHub Actionsは1回も実行されていない**(`threads-research.yml`・`threads-publish.yml`とも run 0件)。理由は正常: research(火曜06:00 JST)はmain昇格前の週にしか機会が無く、publish(毎日21:00 JST)は本レビュー時点でまだ初回前。バグではないが、「自動化システムが動いている」という前提自体、実績ゼロからの評価だと理解すること
- **`product-candidates.md`が古いまま**。2026-09-09に`research.py`を「ジャンル無制限・9カテゴリ」に書き換えたが、**一度も再実行されていない**ため、実際の候補リストは旧・4ジャンル(カイロ/電気毛布/傘/ケトル)10件のまま。当面の投稿案生成もこの古いリストから選ばれる。**「ジャンル無制限」は方針文書上は存在するが、実データには反映されていない**
- **実績データは3投稿(すべて同一商品)、すべて指標ゼロ**。統計的判断ができる状態にない
- **`amazon-links.md`は空**。Amazonは承認済みだが実際には1件もリンク登録されておらず、事実上まだ楽天単独

## 1. ファネル計測状況

| 段階 | 計測状況 |
|---|---|
| 商品選定 | ○ ログあり(`product_name`, `category`) |
| 投稿 | ○ `publish-log.jsonl` |
| インプレッション | ○ `views`(Threads Insights、実機確認済み) |
| 興味(いいね等) | ○ `likes/replies/reposts/quotes/shares` |
| プロフィール訪問 | **✕ 取得不可**(Threads Insights APIに投稿単位のmetricが存在しないと確認済み) |
| リンククリック | **△ 近似値のみ**。`clicks`はリンク・ハッシュタグ・メンション・メディアへのクリックの合算で、アフィリエイトリンク単体ではない |
| 商品ページ閲覧 | **✕ 取得不可**(楽天・Amazon側の管理画面を人間が見るしかない) |
| 購入・成果報酬 | **✕ 未接続**。楽天管理画面のデータと`publish-log.jsonl`を突き合わせる仕組みが存在しない |

**結論**: ファネルの前半(表示〜クリック)は仕組みとして存在するが後半(クリック〜購入〜報酬)は完全にブラックボックス。「インプレッションは増えているのに売上が増えない」を検知する仕組みは存在しない(そもそも売上側のデータが入ってこない)。

---

## 2. 商品選定AI

現在のスコア = `需要(レビュー数、頭打ち40点) + 満足度(レビュー平均40点) + 価格帯20点`。実質「人気商品スコア」であり、「売れそうな商品」ではなく「人気・高評価・価格が手頃な商品」を選んでいるだけ。

欠けている要素:
- **報酬率・想定報酬額**: 一切無い
- **想定CVR・過去実績**: `publish-log.jsonl`にpost_typeやcategoryを記録する仕組みはあるが、商品選定にフィードバックするループが存在しない(片方向で止まっている)
- **競合の多さ・知名度・「知らなかった」感**: 完全に人間(Claude)の主観判断任せで、コードには一切反映されていない
- **過去投稿のクリック率・成約率**: 投稿数が3件(同一商品)しかなく学習不可能な段階

「インプレッションを稼ぐ商品」と「実際に売れる商品」の区別: **現状不可能**(成約データが存在しないため)。

---

## 3. 投稿生成AI

`post-template.md`のルール(悩み→気づき→商品→シーン→CTA、スペック→ベネフィット変換、断定表現の禁止)自体は妥当で、オーナーの過去のレビューを反映して作られている。

ただしこれは「生成ルール」であって「生成AIの性能を測る仕組み」ではない。どのフックが実際にクリックにつながったかを検証する手段が無いため、ルールが正しいかも実証できていない。今の3投稿はいずれも同じ商品・似た文面で、比較材料にすらならない。

---

## 4. パターン別最適化・A/Bテスト

**存在しない。** `post_type`(empathy/discovery/comparison/summary)はログに記録されるが、集計・比較する仕組みがゼロ。「ローテーションではなく成果に応じて配分を変える」設計は、その前段階の「成果を集計する」機能すら無いため着手できない。

A/Bテストは統計的に意味のある判定に最低でも各パターン数十件のサンプルが必要(セクションF参照)。今の投稿ペース(1日1本)では数ヶ月かかる。少ないサンプルで判定するくらいなら「判断不能」と出す設計にすべきだが、現状はその判定ロジック自体が無い。

---

## 5. 売上予測・Amazon/楽天比較・Threads分析の粒度

- **売上予測(期待収益)**: 未実装。計算式自体は簡単に作れるが、「想定報酬率」「想定CVR」の初期値の出所が無く、仮の数字を入れるのは推測になってしまう
- **Amazon vs 楽天比較**: Amazon側の実績が0件(リンク自体が0件)のため比較不能
- **「表示は多いが売れない/表示は少ないが売れる」の発見**: `views`と`clicks`はあるので相関は見れるが、購入(成約)データが無いため「売れる」の判定自体ができない。これが最大のボトルネック

---

## 6. 自動改善ループ・撤退判断

**存在しない。** 現状のループは「商品選定(人力寄り)→投稿生成→投稿→Insights取得」で止まっており、「分析→成功パターン抽出→商品選定への反映」の矢印が引かれていない。撤退判断(低成績カテゴリ・商品の停止)ロジックも皆無。今のデータ量(3投稿)では作っても機能しないため、「まだ作れない」が正確な評価。

---

## 7. 投稿時間・カテゴリ戦略

- **21:00固定の妥当性**: 検証不可能(データなし)。オーナーの初期指示をそのままcronに反映しただけで、根拠となるデータは一切ない
- **カテゴリ戦略**: `category`フィールドはログにあるが集計する仕組みが無い。現状投稿履歴が全て「季節商品」1カテゴリのみで、比較の材料自体が存在しない

---

## 8. 自動化しすぎの問題 — 最重要指摘

`docs/marketing/2026-08-18-ai-affiliate-feasibility.md`(このシステムの最初の実現可能性検証)には、会社自身が明記した以下の記述がある:

> 「勝ちパターンの自動増産」→ **収益性が実証されるまで着手しない**(禁止事項「収益が発生していないのに自動化だけ進める」に直結するため)
> AIが生成した"体験談"は、実際に検証していない限り、断定表現を避ける
> MVPは人間の手動投稿からスタート(自動投稿インフラは後回し)

今回、実績・売上ゼロ、クリック・成約データゼロの段階で完全自動投稿(Phase 2)へ移行した。これは自社方針と正面から矛盾している。技術的には問題なく動くが、コード側の安全装置はPR表記チェックのみで、内容の妥当性(断定表現の有無、事実の正確性)は完全に無検証で毎日投稿される。

現状のリスク配置:

| 項目 | 現状 |
|---|---|
| 商品選定 | AIが生成時に都度判断、記録・検証なし |
| 投稿文生成 | AI完全自動 |
| PR表記 | コードで検証(唯一の自動安全装置) |
| アフィリエイトリンク | AI選択、正当性チェックなし |
| 投稿時間 | 固定(21:00) |
| 投稿実行 | 完全自動、人間確認なし |
| データ収集 | 自動(ただし後半のファネルは欠損) |
| 分析 | 存在しない |
| 戦略変更 | 存在しない(気づいた時だけ手動で変更) |

---

## 9. Amazon APIの切り分け

**「コードの問題」ではない。そもそもAmazon PA-APIを呼ぶコードが1行も存在しない。** 意図的な設計: PA-APIは直近180日で3件以上の成果が無いとアクセス自体を許可されない規約になっており、新規アカウントでは技術的に使用不可能。

現在の実装は最初から「`amazon-links.md`への手動リンク登録」のみで、API連携は「3件成果が貯まったら着手する」という将来タスクとして最初から先送りされている。「API部分に問題がある」という認識は、実装が無いことを指している可能性が高い — バグの修正ではなく、`amazon-links.md`への実リンク登録が唯一必要な作業。

# 最終レポート

## A. 現在の評価: **22/100**(売上最大化の仕組みとして)

OAuth・投稿実行・PR表記検証・基本的なInsights取得といった「配管」部分は動作しており、そこだけなら65点程度。しかし「利益」を最大化する仕組みという評価軸で見ると、ファネル後半が丸ごと欠損し、学習ループ・撤退判断・報酬額を考慮した商品選定・パターン別分析のいずれも存在しないため、大きく減点。今の実態は「投稿を自動化した」に過ぎず、「売上を最大化する」仕組みにはまだなっていない。

## C. 改善案(効果が大きい順)

1. `research.py`を今すぐ再実行(コード変更なし、実行のみ)— ジャンル無制限方針を実データに反映
2. 楽天管理画面のクリック/成果を月次で手動転記する仕組みを作る(自動APIが無い以上、最初はこれしかない)— ファネル後半の可視化
3. 商品スコアに「想定報酬額」(価格×想定報酬率)を追加
4. `publish-log.jsonl`の集計スクリプトを作る(post_type別・category別のviews/likes/clicks合計)
5. 月次振り返りドキュメントのテンプレート化(何を紹介し、何が起きたかを毎月構造化して残す)
6. 撤退ルールをまず文書化(例: 10投稿してCTR相当が全体平均の半分以下なら再検討候補、等)
7. Amazon実リンクを数件登録(2本柱化を実データで進める)
8. A/Bテストの前段階として文面パターンをタグ付けし、後で比較できる形にする(既存post_typeの粒度で十分、まずは溜める)

## E. 今は実装しなくていいもの(過剰設計)

- A/Bテストの本格エンジン(統計的検定ロジック等)— サンプル数(3投稿)が絶望的に不足
- 投稿時間の動的最適化 — 同上
- 「AIによる自己評価」の自動改善ループ — 実データが無い状態で回すと、根拠のない自己満足のループになる
- Amazon PA-API連携 — 規約上不可能、着手時期尚早
- 複数SNSへの展開 — Threads単体すら検証できていない段階

## F. データ不足で判断できないもの

| 最適な投稿時間 | 複数時間帯×各20投稿程度 |
| カテゴリ別収益性 | 各カテゴリ最低10〜20投稿 |

| 商品選定スコアの妥当性検証 | 実際のクリック数・成約数が最低数十件 |

現在の投稿ペース(1日1本)だと、post_type別の判断だけで2〜4ヶ月かかる計算。

---

**結論**: 技術的な「配管」はよくできているが、「利益を最大化する仕組み」としては、成約データが入ってこない限りどう改善しても頭打ちになる。次の一手は新機能の追加ではなく、(1)`research.py`の再実行、(2)楽天の成果を人力ででも見える化すること。この2つをやらない限り、他のどんな改善(A/Bテスト、AI改善ループ等)も「何を根拠に良いと言えるか」が無いまま空回りする。
