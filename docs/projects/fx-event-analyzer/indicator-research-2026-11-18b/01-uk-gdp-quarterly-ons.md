# 英国 GDP 四半期(ONS)の導入調査(第 2 版、2026-11-18)

担当 D。調査・設計のみ(コード・migration・DB・DEV の変更なし)。確認した事実と、確認できなかったことを分けて書く。

**第 2 版の変更**(C の独立レビューによる): ① 改定確認期間の再設計(長期の改定の実測を反映)、② データ取得先の修正(初回値と改定確認で別)、③ 12/23 の確認手順、④ versions の重複ラベルの注記、⑤ ONS ライセンスの確認範囲の明記。第 1 版の「ukea・qna は古い」は誤りだったので訂正した(§3)。

## 1. 結論(先に)
- **公式の四半期前期比(%)の系列がある**(ONS の時系列 API、CDID **IHYQ**)。計算は要らない。
- **実装可能**。ただし既存の ONS アダプターは月次(`months`、'YYYY MON')だけを読むので、**四半期(`quarters`、'YYYY Qn')を読む拡張**が要る。
- **改定は非常に遅くまで続く**(§5)。**初回値の取り込みの期限とは完全に分離**して、改定確認の期間を長く取る(暫定 1,700 日)。ただし、この期間は**公式 API の値を使う改定確認だけ**に効き、QA-1 の状態修復の範囲は**広げない**(§6)。
- **データセット ID が公表ごとに更新先が違う**(§3)。初回値は `pn2`、改定確認は `pn2`・`qna` のうち releaseDate が新しい方。`datasetId` と公表日(ロンドン時間の日付)の照合を必須にする。
- 推奨: 導入する(優先度は中)。

## 2. 公式ソースと数値系列(実 API、2026-11-18)
| 系列 | 内容 | 値(2026-11-12 公表分) |
|---|---|---|
| **IHYQ**(推奨) | GDP 前期比、CVM、季節調整、%(unit `%`) | 2026 Q3 = **0.7**、Q2 = 0.5、Q1 = 0.6、2025 Q4 = 0.0 |
| IHYR | 当年の第 4 四半期に対する伸び | 2026 Q3 = 1.9 |
| IHYP | 前年比(**年次**のみ) | 2025 = 1.2 |
| ABMI | GDP の水準、CVM、季節調整、£m | 2026 Q3 = 749,999 |
| ED3H(月次データセット MGDP) | 「3 か月/前の 3 か月」。四半期の最終月の値は四半期の前期比と同じ | 参考。独自の系列として使わない |
- 公式の発表文「UK real GDP is estimated to have increased by 0.7% in Quarter 3 (July to Sept) 2026, following growth of 0.5% in Quarter 2」と IHYQ が一致。
- 四半期ごとの前年同期比の公式の系列は、見つけていない(IHYP は年次)。
- 取得: `https://www.ons.gov.uk/economy/grossdomesticproductgdp/timeseries/ihyq/<データセット ID>/data`(JSON、鍵なし)。

## 3. データセット ID の違い(第 1 版の誤記を訂正)
同じ IHYQ が、**データセットごとに別の公表で更新される**。2026-11-18 の実測:

| データセット(`description.datasetId`) | データセットの名前(`datasetUri`) | `releaseDate`(UTC) | ロンドンの日付 | 最新の四半期 | `nextRelease` の記載 |
|---|---|---|---|---|---|
| **PN2** | secondestimateofgdp | 2026-11-12T00:00Z | 2026-11-12 | **2026 Q3 = 0.7** | 22 December 2026 |
| **QNA** | quarterlynationalaccounts | 2026-09-29T23:00Z | **2026-09-30**(BST) | 2026 Q2 = 0.5 | 12 November 2026 |
| UKEA | unitedkingdomeconomicaccounts | 2026-09-29T23:00Z | 2026-09-30 | 2026 Q2 = 0.5 | 22 December 2026 |
- **第 1 版の訂正**: 「ukea・qna は古い」は誤り。**qna と ukea は、9/30 の公表(四半期国民経済計算・UK economic accounts)で更新されたもの**で、9/30 時点では最新だった。今回 11/12 に更新されたのは `pn2` だけ。「古い」のではなく、**公表ごとに更新されるデータセットが違う**。
- 同じ四半期の値が、更新のタイミングによってデータセット間で違うことがある(例: 2026 Q2 は、8 月の pn2 で 0.4、9/30 の qna・ukea で 0.5、11/12 の pn2 で 0.5)。
- `nextRelease` の記載は、データセットごとに別の予定を指し、**更新先の予告として信用しない**(qna の「12 November 2026」は、11/12 に qna が更新されていないので、そのとおりにならなかった)。

### 3.1 取得先の設計(C の指摘)
| 用途 | 取得先 | 条件 |
|---|---|---|
| **初回値**(初回推計の日: 2027-02-12・05-14 …) | **`pn2`** | `datasetId` が `PN2`。`releaseDate` のロンドンの日付 = 予定表の公表日。最後の四半期の行の `updateDate` が公表日。対象四半期 = 予定表の referencePeriod |
| **改定確認** | `pn2` と `qna` を**両方取得**し、`releaseDate` が**新しい方**を使う | 取得した応答の `datasetId` が許可リスト `{PN2, QNA}` にあること(`UKEA` など他は使わない)。許可リストに無い・取得に失敗した方は無視し、残りだけで判断(両方失敗なら何もしない) |
- `releaseDate` は **UTC の時刻**(夏時間では前日 23:00Z)。**ロンドン時間の日付に直して**比べる(既存の `localDate(…, 'Europe/London')` と同じ)。
- 2 つの releaseDate が同じ日なら `pn2` を優先する(初回推計の日の値)。
- 許可リストを `datasetId` で検証するのは、データセットの取り違えと、URL の誤りによる別の系列・別の版の混入を防ぐため。

### 4.1 12/22 公表後の確認手順(12/23 に実施する、調査のみ)
12/22 の公表が、どのデータセットを更新するかを、実 API で確認する。**実装の最終判断の前提**。

1. **取得**: 次の 3 つを取得する。
   - `…/timeseries/ihyq/pn2/data`
   - `…/timeseries/ihyq/qna/data`
   - `…/timeseries/ihyq/ukea/data`
2. **各応答で読む**: `description.datasetId`、`description.releaseDate`(**ロンドンの日付に直す**)、`description.nextRelease`、`quarters` の末尾 3 行(`value`・`updateDate`)、`versions` の件数と最後の `label`・`updateDate`。
3. **確認する点**:
   - [ ] `qna`・`ukea` の releaseDate が **2026-12-22**(ロンドン)になっている。
   - [ ] **2026 Q3 の値**: qna・ukea での値(改定の有無)と、pn2 の 0.7 との差。
   - [ ] **`versions` の件数**が、各データセットで増えた(qna は 44 → 45、ukea は 43 → 44 の見込み)。増えていなければ、更新されていない。
   - [ ] **`pn2` が 2026-11-12 のまま**か(releaseDate・versions が変わっていないか)。変わっていれば、pn2 も 12/22 に更新されることになり、§3.1 の「pn2 は初回推計の日だけ」の前提を直す。
4. **判断**: 上の結果で、**改定確認に `pn2`・`qna` のどちらが最新になるか**が分かる。許可リスト `{PN2, QNA}` の方針(§3.1)が妥当かを確認し、本書に結果を追記する。
5. 取得は読み取りだけ(書き込みなし)。

## 5. 改定履歴と改定頻度(実測)
### 5.1 versions の読み方(注意)
- 系列ページの `versions` 配列は **47 要素**だが、**`v15` が 2 回載っている**(同じ `uri`・同じ `updateDate` 2019-05-10)。**ラベルの重複を除くと v1〜v46 の 46 版**。
- 各 `vN` の `updateDate` は、**その版を次の版に置き換えた公表の日時**を指す(例: v46 = 2026-11-12。`/previous/v46/data` の中身は 2026-08-12 公表のデータ)。**現行版(`…/ihyq/pn2/data`、2026-11-12 公表)は `versions` に載らない**。`/previous/v47/data` は存在しない(404)。したがって、**データ点は過去版 46 + 現行 1 = 47**。
- v16(2019-05-10T08:59:07Z)は、v15 の約 30 分後の版(同日)。**原因は未確認**。
- 実装で版を数える・一覧するときは、**ラベルの重複を除く**こと。

### 5.2 改定の実測(D の再集計)
**方法**: IHYQ の pn2 の 47 データ点(過去版 v1〜v46 と現行)を、公表日(`description.releaseDate`)の順に並べ、各四半期について、**「最初に現れた版の公表日」から、「値が前の版と違った版の公表日」までの日数**を数えた。四半期を、**ある版で最新の四半期として初めて現れたもの(46 四半期)**に限った。

| 指標 | 値 |
|---|---|
| 対象の四半期 | 46 |
| 改定の件数 | 204(1 四半期あたり平均 約 4.4 回) |
| 改定の日数の中央値 | 456 日 |
| **270 日を超える改定の割合** | **76%** |
| 365 日 / 730 日 / 1,095 日 / 1,460 日 を超える割合 | 59% / 39% / 29% / 23% |
| **1,700 日を超える割合** | **19%**(18.6%) |
| **最長** | **3,458 日**(2016 Q1: 0.4 → 0.5 が 2026 年に改定) |
- **C の集計**(270 日超の改定が 64%、最長 1,645 日)と、**D の再集計(76%、最長 3,458 日)は、定義の違いで数が合わない**(C の定義の詳細は未確認。四半期の範囲・版の範囲が違う可能性)。**どちらでも、改定は 1 年以上後にも頻繁に入る**という結論は同じ。
- **長期の改定の主因は、毎年の大規模な改定(ONS の Blue Book、毎年 9 月の四半期国民経済計算)**とみられる。過去数年分が一度に動く。
- 最近の例(実 API の版): 2025 Q4 は 0.1(2026-02)→ 0.2(05 月)→ 0.1(08 月)→ **0.0(2026-11)**。2026 Q2 は 0.4(2026-08)→ **0.5(2026-11)**。

## 6. 改定確認期間の設計(`revisionLookbackDays`)
- **公式 API の値を使う改定確認だけ**の期間。**初回値の期限(`maxDaysAfterRelease`)とは完全に分離**する。`GB_GDP_QOQ` には、**`maxDaysAfterRelease` を明示**(7 日)し、改定確認の期間を延ばしても、初回値として受け付ける範囲は変わらない。ONS のパーサーは、さらに API の公表日と予定の公表日の一致を要求する。
- **暫定候補: 1,700 日**(約 4.7 年)。
  - 根拠: 改定の約 81% を含む(1,700 日を超えるのは 18.6%)(§5.2)。最長(3,458 日)までは含まない。
  - **全期間を網羅する期間は決められない**(改定は 9.5 年後にも入る)。1,700 日は、費用と網羅の釣り合いで決める暫定値で、**毎年 9 月の Blue Book の後に見直す**。
  - 代案: 日数ではなく、**直近 N 件(例 24 件)の初回推計のイベント**を対象にする。四半期の指標では、日数と件数は同じ意味になるので、日数のままでよい。
- **費用・処理件数・保存履歴への影響**(1,700 日の評価)

| 項目 | 評価 |
|---|---|
| 対象イベント数 | 四半期の初回推計のイベントは年 4 件。1,700 日で **最大 約 19 件**(イベントは導入後(2027-02-12 以降)に作られるので、導入直後は 1〜2 件) |
| 公式 API の呼び出し | **変わらない**: 同じ応答(pn2 と qna の各 1 回)を、全イベントで使う。1 回の実行あたり 2 回 |
| DB の問い合わせ | イベントごとに `getReleaseSnapshot` と `latestRevisionValues` の 2 回。最大 19 件 × 2 = **約 40 回/実行**(現在の 45 日では 2〜4 回)。実行が日次なら**無視できる**。負荷を下げたい場合は、「`releaseDate` が直近 3 日以内のときだけ改定確認を行い、週に 1 回は全件を確認する」ゲートを設ける(公表の無い日は値が変わらないため) |
| 保存履歴(`event_revisions`) | **値が変わったときだけ**書く。実測で 1 回の公表あたり約 4.4 件、9 月は多い。19 イベント × 年数回でも**年に数十行**。サイズは無視できる |
| 表示への影響 | 古いイベントに、後から改定が付く。アプリの過去比較で「改定された」と見えるようになる。これは、改定の履歴として意図した挙動 |
- **QA-1 の状態修復の範囲は広げない**(C の指摘)。
  - `revisionLookbackDays = 1,700` は、**公式 API の値を使う処理**(初回値の取り込み・改定確認)だけに適用する。
  - **状態修復は `repairLookbackDays`(既定 90 日)**で別に決まり、`GB_GDP_QOQ` の 1,700 日の影響を受けない。したがって、**古い stuck 行(90 日より古い)を 1,700 日まで自動で直すことはない**。
  - 設計の詳細は、`claude/fx-indicator-research-d` の `03-revision-lookback-per-indicator-design.md`(第 2 版)。

## 7. 取得 API・形式
- JSON(ONS の `…/data`)。鍵なし。`quarters` 配列(`date` = '2026 Q3'、`value`、`updateDate`、`sourceDataset`)。月次は `months`。
- `updateDate` は、値が変わらなくても公表日に更新される(2025 Q4 の行も 2026-11-12)ので、**改定の検知には使えない**(値の比較が必要)。初回値の確認には使える。
