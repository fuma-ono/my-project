- **公式の % がそのまま取れる**(系列 `CAPUTL.B50001.S` = 総合の設備稼働率、季節調整済み、単位 Percentage)。IP の前月比のような計算は要らない。

## 4. 取得経路(XML zip のみ)
### 4.1 Fed の DDP の縮小(2026-11-18 に確認)と、CSV を含めない理由
- **Build Your Package は廃止済み**。**preformatted data package(プリセット CSV)は 2027-03-31 に廃止**。**DDP のページは 2027-07-01 に削除**。出典: https://www.federalreserve.gov/datadownload/default.htm ・ https://www.federalreserve.gov/data/data-download-fred-information.htm
- **系列名での固定 URL 指定は不可**(`series=CAPUTL.B50001.S` は HTTP 400)。ハッシュは新規に作れない。
- したがって、**導入の約 3 か月後(2027-03-31)に使えなくなる経路は、設計に含めない**。**CSV プリセットも、フォールバックの経路としても採用しない**(第 3 版までの「CSV → XML zip のフォールバック」は削除)。
- 残る経路: **G.17 の公表ページの XML zip**(Fed が「XML は公表ページから引き続き提供」と明記)。DDP の zip(`Output.aspx?rel=G17&filetype=zip`)は、2027-07-01 に消え、`Last-Modified` が取得時刻で更新確認に使えないので**使わない**。FRED の API は、データの保存・再配布の規約上、採用しない見込み。

### 4.2 取得と照合
- URL: `https://www.federalreserve.gov/releases/g17/data/FRB_g17_xml.zip`(8.6MB 圧縮、展開後は XML で約 10 倍)。中に `G17_data.xml`・`G17_struct.xml`・各表の xsd。
- **照合(必須。1 つでも欠けたら保存しない)**: `G17_data.xml` の SDMX-ML で、
  - `<kf:Series SERIES_NAME="CAPUTL.B50001.S" … UNIT="Percentage" SA="SA">` に一致する系列が**ちょうど 1 本**。
  - 対象の観測の `OBS_STATUS` が `A`(正常)。`TIME_PERIOD` が月末の日付で、対象月と一致。値が数として読める。
  - `UNIT` が `Percentage`(単位の照合は必須)。
- 照合に失敗した場合は、**何も書かない**(PENDING のまま)。エラーとして記録し、人が確認する。

### 4.3 HEAD と条件付き GET による更新確認
2026-11-18 に、`FRB_g17_xml.zip` で試した結果(1 回の試行。**仕様の保証ではない**):
| 試験 | 結果 |
|---|---|
| HEAD | 200。`Content-Length: 8612001`、`ETag: "51974dc9e76dd1:0"`、`Last-Modified: Tue, 17 Nov 2026 14:15:07 GMT`、`Accept-Ranges: bytes` |
| 条件付き GET(`If-Modified-Since: Tue, 17 Nov 2026 14:15:07 GMT`) | **304**(更新が無ければ 8.6MB を取らずに済む) |
- **更新確認の手順(案)**:
  1. 実行のたびに、まず **HEAD**(数百バイト)を送る。
  2. `ETag`・`Last-Modified` が、**前回の成功した実行で記録した値と同じ**なら、**何もせず終了**(取り込み済み、または未更新)。
  3. 違えば、**条件付き GET**(`If-None-Match`・`If-Modified-Since`)で本体を取る。304 なら終了。
  4. 本体を取ったら、§4.2 の照合を通し、通ったときだけ保存。**取得に成功してから**、新しい `ETag`・`Last-Modified` を記録する(失敗した回に記録しない)。
- **前回値の保管**: 社内 PC に残さない方針のため、**DB の取り込みログ(`ingestion_logs.details`)に記録**する(例: `fed_g17_etag`・`fed_g17_last_modified`)。新しい表・列は不要。
- **これは 1 回の観察**。Fed が `ETag`・`Last-Modified` を、**公表のときだけ**更新する保証は確認できない。複数回(公表日の前後)の観察が要る(§11)。変わらない場合は、公表日と翌日だけ本体を取る運用にする。
- 取得頻度の方針: 公表日と翌日は、HEAD を数回。それ以外の日は、実行しても HEAD だけ(負荷が小さい)。

## 5. 改定履歴と改定頻度(現状)
- **通常の改定**: 毎回、直前の数か月が改定される。今回の発表の表(Previous estimates の行)で、**直前の公表(10/16)から 11/17 の間に、8 月が 76.4 → 76.3、9 月が 76.9 → 76.8 に動いた**(いずれも -0.1)。
- XML zip は**最新版だけ**で、過去の版は取れない。FRED/ALFRED は規約上、保存できない(先の調査)。したがって、**初回値は自分で保存し、後の値は `event_revisions` に記録する**。
- **11/24 の年次改定(Fed の告知、2026-11-18 に確認)**: IP の基準年は 2022(現在 2017=100)。**稼働率・設備能力**は、Census の四半期の設備稼働調査(2025 年第 4 四半期まで)と USGS・DOE などの新しいデータで改定される。推計の方法の変更は「1972 年から現在までの指数」に影響する。**改定の幅は事前には不明**。
- 改定前の値を比較の基準として保存した(§12 の表)。

### 5.1 通常の改定と年次改定の扱いの違い(分けて扱う)
| | **通常の改定**(毎月) | **年次改定**(毎年 1 回、今回 2026-11-24) |
|---|---|---|
| 内容 | 公表のたびに、直前の数か月が小さく動く | 基準年・設備能力・季節要因などが更新され、**全期間の水準が動く** |
| 検出の範囲 | `revisionLookbackDays` = **56 日**(月次の最長間隔 35 日 + 21 日)。直近 1〜2 件のイベント | **保存済みの全イベント**(実行時の指定で、年次改定の実行だけ窓を深くする) |
| きっかけ | 毎月の公表日(公表予定の表) | **事前に登録した年次改定の日**(§6.3)。公表予定の表には**入れない** |
| 予定表への登録 | する(公表日ごとにイベント) | **しない**(イベントを作らず、初回値を付けない) |

| 値の保存 | 変わったときだけ `event_revisions` に ACTUAL | 同じ(全イベントについて、変わったものだけ)。**初回値(RELEASE スナップショット)は書き換えない** |
| 通知・確認 | 通常のログ | **件数と最大の差をログ・通知に出し、人が確認** |
| 過去履歴 | 該当なし | 改定後の公式の履歴は、**初回値として取り込まない**(§6.4) |

## 6. 年次改定の記録設計
### 6.1 原則
1. **初回値は不変**。公表日に保存した値(`RELEASE` スナップショット)は、年次改定で変わっても書き換えない。
2. **改定は `event_revisions` に別の履歴**として足す(同じ値は足さない)。
3. **改定後の公式の過去履歴を、初回値として扱わない**。過去のイベントの初回値を、改定後の値で置き換えない。
4. 初回値の系列(各月の公表時の値)と、改定後の公式の系列は**別のもの**として保存・表示する。混ぜない。

### 6.2 年次改定の `source` の識別
- `event_revisions.source`(既存の列。スキーマの変更は不要)に、**通常の改定と区別できる文言**を入れる。
  - 通常の改定: `Federal Reserve Board`
  - **年次改定: `Federal Reserve Board (annual revision 2026-11-24)`**(日付は、事前登録した日)
- 画面・集計・監査で、年次改定による改定だけを抽出できる(`source` の文言で絞る)。

### 6.3 年次改定日の事前登録と、定時実行による自動切替
- **事前登録**: 年次改定の日を、**コードで確認する設定(CODE-REVIEWED CONFIG)**に登録する(人が毎年、公表ページの告知「Revision of Industrial Production and Capacity Utilization」を読んで書く)。
  ```ts
  export const FED_G17_ANNUAL_REVISIONS = ['2026-11-24'] as const; // 公表ページの告知(2026-11-18 確認)
  ```
  公表予定の表(通常の公表日)とは**別の設定**。
- **自動切替(定時実行が承認・実装された後)**: 取り込みジョブが、毎回の冒頭で次を判定する。
  1. 登録した日付のうち、**今日以前で、まだ年次改定の処理を済ませていない日**があるか(処理済みの印は `ingestion_logs.details` の `annual_revision_done`)。
  2. ある場合、HEAD で zip の `Last-Modified`(ET の日付)が**その登録日以降**か確認する(= 改定後のデータが zip に入った印)。**入っていなければ、通常の確認に戻り、翌回に再判定**。
  3. 入っていれば、**年次改定用の深い確認に自動で切り替える**: 保存済みの**全イベント**を対象(実行時の窓を深くする)に、改定を `event_revisions` に記録(`source` は §6.2)。処理済みの印を記録。件数と最大の差を、ログ・通知に出す。
  4. **この通常の改定と年次改定の窓の切替は、1 回の実行の中で、通常の確認より先**に行う(年次改定の動きを、通常の改定の窓で一部だけ拾って混ざらないように)。
- **前提(重要)**: 公式の統計の取り込み(official-values・JP CPI・Eurostat)は、**現在は手動実行(`workflow_dispatch`)だけで、定時実行は無い**。したがって、**自動切替は、定時実行が承認・実装されるまで動かない**。それまでは、**同じ処理を、手動の実行の入力(例 `--annual-revision 2026-11-24`)で行う**(人が、登録日の翌日以降に実行する)。
- **書き込みを伴う年次改定の実行は、初回は dry-run → 件数と差を HQ が確認 → 本実行**(承認後)。

### 6.4 過去履歴の取り込み(必要な場合)
- 過去の月の値(前回値・12 か月の推移)が要る場合は、**年次改定の後の公式データから一括で取り込む**(改定の前後の値を混ぜない)。
- **初回値(`RELEASE` スナップショット)としては取り込まない**。取り込んだ値は、**「改定後の公式の履歴(vintage = 2026-11-24 の年次改定後)」であることを識別できる形**で別に持つ。
- 既存の受け皿: `official_observations` 表(`source`・`series_id`・`period_start`・**`as_of_date`**(いつ時点の値か)・`value`)。**`as_of_date` に改定の日(2026-11-24)を入れれば、vintage を識別できる**。ただし `source` は `'FRED'`・`'BLS'` に限定(CHECK 制約、migration 20261015000003)。**`'FED'` を足すには DB スキーマの変更(migration)が必要で、HQ の個別承認が要る**。承認が出ない場合は、過去履歴を取り込まない(各月の初回値だけを持つ)。
- **受け皿が決まるまで、過去履歴の取り込みはしない**。

### 6.5 翌年以降
- 毎年の年次改定の後に、①改定前後の差の確認(直近 12 か月)②登録した改定の日の更新 ③この節の運用の見直し、を行う。

## 7. 公表の延期・NA への対応
- **公表予定の表は、人が公式の日程を確認して更新する運用でよい**。公式の日程は release dates ページ(§3)で、年 1 回、翌年分が出る。公表が延期されたときは、人が表を更新する。
- 自動の挙動(日程の更新を待たずに、誤った値を出さないため):
  - **公表が反映されていない**(最後の月が対象月より前): **何も書かない**(PENDING のまま)。次の実行で取り直す。
  - **NA・欠測**: XML の `OBS_STATUS` が `A` でない、値が数でない → **その月は「値なし」**として何も書かない。**補完・前回値の流用はしない**。
  - **日程より遅れた公表**: 初回値として受け付ける期限(`maxDaysAfterRelease`、案: **10 日**)を設ける。期限を過ぎて初めて現れた値は、**初回値としない**(改定後の値の可能性)。人が表を更新したうえで、判断する。
  - **日程にない日の更新**(年次改定など): 初回値にしない(§6)。
- 取り込みの失敗・延期が続くとき(期限を過ぎても未公表)は、**通知・ログに出して人が確認**する。

## 9. 実行頻度の前提と、既存基盤との適合性
| 項目 | 内容 |
|---|---|
| **実行頻度(前提)** | official-values・JP CPI・Eurostat の取り込みは、**現在は手動実行だけ**(`workflow_dispatch`、`fx-event-analyzer-ingestion.yml` で確認)。**定時実行の追加は、既存の定期実行ワークフローの変更で、HQ の別承認**。**日次・定時の実行を前提にした記述(HEAD の毎日の確認、年次改定の自動切替)は、定時実行が承認・実装されるまでは前提条件**であり、それまでは人が手動で実行する |
| 取得 | 新しいアダプターが必要(XML zip の展開・SDMX-ML の解析、HEAD・条件付き GET)。ライブラリの追加の可能性が高い |
| 公表日の照合 | API に更新日が無い。公表予定の表 + 最後の月の一致 + zip の `Last-Modified` で代用。ONS・ABS より弱い |
| 初回値の保存・改定 | 既存の `official-values` の枠(`parseForRelease`・`valueForPeriod`)に、新しい取得元として載せられる |
| 改定の期間 | 月次なので `revisionLookbackDays` = 56。年次改定の実行だけ深くする(§6.3) |
| migration | 指標 1 行 + 通貨ペア(USDJPY・EURUSD)。過去履歴の受け皿(§6.4)は別の承認 |
