## 1. 結論(先に)
- **公式の % がそのまま取れる**(系列 `CAPUTL.B50001.S` = 総合の設備稼働率、季節調整済み、単位 Percentage)。IP の前月比のような計算は要らない。
- 取得経路は **XML zip を長期の本線**とし、**CSV プリセットは 2027-03-31 までの暫定の最適化**(任意)。CSV が使えない・照合に失敗したときは、**XML zip にフォールバック**する(§4)。
- **毎年の年次改定は、水準そのものを動かす**。初回値は不変、改定は `event_revisions` に別の履歴、**改定後の公式の過去履歴は初回値と混ぜない**(§6)。
- 推奨: **2026-11-24 の年次改定の後**に導入する。最初に保存するのは 2026-12-16 公表(11 月分)から。
- 注意: 稼働率は IP の添え物で、単独の FX への影響は IP の変化率より小さい見込み。優先度は中〜低(HQ の判断)。

### 4.3 フォールバックの条件(CSV → XML zip)
次のどれかのとき、CSV の値を**使わず**、XML zip に切り替える(同じ実行の中で)。
1. HTTP が 200 でない、応答が空、CSV として読めない(**ハッシュの失効・Fed の仕様変更**を含む)。
2. **照合の失敗**(§4.4)。
3. 最後の月が、予定表の対象月と一致しない(**公表が反映されていない**ときは、フォールバックではなく「未公表」として何も書かない — §7)。
- 2 つの経路の値が**食い違う**ときは、**保存しない**(エラーとして記録し、人の確認)。

### 4.4 照合(必須。1 つでも欠けたら保存しない)
**CSV**(列の見出しは `"Description:","Unit:","Multiplier:","Currency:","Unique Identifier:","Series Name:",<月>…`)
- `Unique Identifier:` の値が **`G17/CAPUTL/CAPUTL.B50001.S`** と**完全一致**し、`Series Name:` が `CAPUTL.B50001.S`。
- `Unit:` が **`Percentage`**、`Multiplier:` が `1`。
- 見出しの月が `YYYY-MM` で、最後の月が対象月。値が数として読める。
- 行が 1 本に決まる(同じ系列の重複・欠落があれば保存しない)。

**XML zip**(`G17_data.xml`)
- `<kf:Series SERIES_NAME="CAPUTL.B50001.S" … UNIT="Percentage" SA="SA">` に一致する系列がちょうど 1 本。
- `OBS_STATUS` が `A`(正常)の観測だけ。`TIME_PERIOD` が月末の日付で、対象月と一致。

## 5. 改定履歴と改定頻度(現状)
- **通常の改定**: 毎回、直前の数か月が改定される。今回の発表の表(Previous estimates の行)で、**直前の公表(10/16)から 11/17 の間に、8 月が 76.4 → 76.3、9 月が 76.9 → 76.8 に動いた**(いずれも -0.1)。
- DDP・XML zip は**最新版だけ**で、過去の版は取れない。FRED/ALFRED は規約上、保存できない(先の調査)。したがって、**初回値は自分で保存し、後の値は `event_revisions` に記録する**。
- **11/24 の年次改定(Fed の告知、2026-11-18 に確認)**: IP の基準年は 2022(現在 2017=100)。**稼働率・設備能力**は、Census の四半期の設備稼働調査(2025 年第 4 四半期まで)と USGS・DOE などの新しいデータで改定される。推計の方法の変更は「1972 年から現在までの指数」に影響する。**改定の幅は事前には不明**。
- 改定前の値を**比較の基準として保存**した(§10 の表)。

### 5.1 通常の改定と年次改定の扱いの違い(分けて扱う)
| | **通常の改定**(毎月) | **年次改定**(毎年 1 回、今回 2026-11-24) |
|---|---|---|
| 内容 | 公表のたびに、直前の数か月が小さく動く(例: 8 月 76.4 → 76.3、9 月 76.9 → 76.8) | 基準年・設備能力・季節要因などが更新され、**全期間の水準が動く** |
| 検出の範囲 | `revisionLookbackDays` = **56 日**(月次の最長間隔 35 日 + 21 日)。直近 1〜2 件のイベント | **保存済みの全イベント**(実行時の指定 `deps.revisionLookbackDays` を、年次改定の実行で**一度だけ**長くする) |
| きっかけ | 毎月の公表日(公表予定の表) | **人が登録した年次改定の日**(公表ページの告知を毎年確認)。公表予定の表には**入れない** |
| 予定表への登録 | する(公表日ごとにイベント) | **しない**(イベントを作らず、初回値を付けない) |
| `event_revisions.source` | 既定の文言(「Federal Reserve Board」) | **年次改定と分かる文言**(例: 「Federal Reserve Board (annual revision 2026-11-24)」)。スキーマの変更は不要 |
| 値の保存 | 変わったときだけ `event_revisions` に ACTUAL | 同じ(全イベントについて、変わったものだけ)。**初回値(RELEASE スナップショット)は書き換えない** |
| 通知・確認 | 通常のログ | **年次改定の実行は、件数と最大の差をログ・通知に出し、人が確認**する |
| 過去履歴 | 該当なし | 改定後の公式の履歴は、**初回値として取り込まない**(§6.3) |
- 年次改定の日の**翌日以降**に、年次改定の実行を一度だけ行う(日付を設定に登録しておく)。**年次改定の直後の通常の公表**(今回は 2026-12-16)より前に済ませる。順序を逆にすると、通常の改定の確認の窓(56 日)が年次改定の動きを一部だけ拾い、区別がつかなくなる。
- 年次改定を**通常の改定として窓の中だけで拾わない**(取りこぼしと、改定の理由の混在を防ぐため)。

## 6. 年次改定の記録設計(毎年の改定を、どう記録するか)
Fed は**毎年**、年次改定を行う(今回は 11/24)。毎回、**全期間の水準が動く**。次の原則で記録する。

### 6.1 原則
1. **初回値は不変**。公表日に保存した値(`RELEASE` スナップショット)は、年次改定で変わっても書き換えない。
2. **改定は `event_revisions` に別の履歴**として足す(既存の方針。同じ値は足さない)。
3. **改定後の公式の過去履歴を、初回値として扱わない**。過去のイベントの初回値を、改定後の値で置き換えない。
4. 初回値の系列(各月の公表時の値)と、改定後の公式の系列(年次改定後の最新の値)は**別のもの**として保存・表示する。混ぜない。

### 6.2 年次改定の日の処理
- **年次改定の日は、通常の公表日ではない**。**公表予定の表に入れない**(その日にイベントを作らず、初回値を付けない)。
- 運用: 人が、毎年、公式の告知(公表ページの「Revision of Industrial Production and Capacity Utilization」)を確認し、**年次改定の日付を設定に登録する**(例: `annualRevisions: ['2026-11-24']`)。
- 年次改定の日(の翌日以降)の取り込みで、**改定確認の対象を広げる**(通常は `revisionLookbackDays` = 56 日の範囲だけ。**年次改定の実行では、保存済みの全イベント**を対象にする: 実行時の指定 `deps.revisionLookbackDays` を一度だけ長くする)。これで、年次改定による全イベントの値の変化が、`event_revisions` に入る。
- 改定の `source` には、**通常の改定と区別できる文言**を入れる(例: 「Federal Reserve Board (annual revision 2026-11-24)」)。`event_revisions.source` は既存の列なので、**スキーマの変更は要らない**。

### 6.3 過去履歴の取り込み(必要な場合)
- 過去比較のために、過去の月の値(前回値・12 か月の推移)が要る場合がある。**年次改定の後の公式データから一括で取り込む**(改定の前後の値を混ぜない)。
- **初回値(`RELEASE` スナップショット)としては取り込まない**。取り込んだ値は、**「改定後の公式の履歴(vintage = 2026-11-24 の年次改定後)」であることを識別できる形**で別に持つ。
- 既存の受け皿: `official_observations` 表(`source`・`series_id`・`period_start`・**`as_of_date`**(いつ時点の値か)・`value`・`release_status`・`fetched_at`)。**`as_of_date` に改定の日(2026-11-24)を入れれば、vintage を識別できる**。
  - ただし、この表の `source` は `'FRED'` と `'BLS'` に限定されている(CHECK 制約、migration 20261015000003)。**Fed 用に `'FED'` を足すには、DB スキーマの変更(migration)が必要**。これは **HQ の個別承認が要る事項**。
  - 承認が出ない場合の代替: 過去履歴を取り込まない(各月の初回値だけを持つ)。この場合、導入前の月の「前回値」は表示できない。
- **受け皿が決まるまで、過去履歴の取り込みはしない**。

### 6.4 翌年以降
- 毎年の年次改定の後に、①改定前後の差の確認(同じ取得で、直近 12 か月)②登録した改定の日の更新 ③この節の運用の見直し、を行う。

## 7. 公表の延期・NA への対応
- **公表予定の表は、人が公式の日程を確認して更新する運用でよい**(C の確認どおり)。公式の日程は release dates ページ(§3)で、年 1 回、翌年分が出る。公表が延期されたときは、人が表を更新する。
- 自動の挙動(日程の更新を待たずに、誤った値を出さないため):
  - **公表が反映されていない**(最後の月が対象月より前): **何も書かない**(PENDING のまま)。次の実行で取り直す。
  - **NA・欠測**: CSV のセルが数でない(`ND`・`NA`・空など)、XML の `OBS_STATUS` が `A` でない → **その月は「値なし」**として何も書かない。**補完・前回値の流用はしない**。
  - **日程より遅れた公表**: 初回値として受け付ける期限(`maxDaysAfterRelease`、案: **10 日**)を設ける。期限を過ぎて初めて現れた値は、**初回値としない**(改定後の値の可能性)。人が表を更新したうえで、判断する。
  - **日程にない日の更新**(年次改定など): 初回値にしない(§6.2)。
- 取り込みの失敗・延期が続くとき(期限を過ぎても未公表)は、**通知・ログに出して人が確認**する。

## 9. 既存基盤との適合性・リスク
| 項目 | 評価 |
|---|---|
| 取得 | 新しいアダプターが必要(XML zip の展開・SDMX-ML の解析、CSV の照合)。ライブラリの追加の可能性が高い |
| 公表日の照合 | API に更新日が無い。公表予定の表 + 最後の月の一致で代用。ONS・ABS より弱い |

| migration | 指標 1 行 + 通貨ペア(USDJPY・EURUSD)。過去履歴の受け皿(§6.3)は別の承認 |

**リスク**
1. 年次改定の幅が不明(11/24 の後に確認)。
2. 公表時刻が未確認(§3)。
3. XML zip のサイズと、自動取得の頻度の指針が未確認。
4. プリセット CSV のハッシュの失効(2027-03-31 まで、または Fed の都合で前倒し)→ フォールバックで吸収。
5. 公表日の照合が弱い。
6. 稼働率単独の FX への影響の小ささ(優先度)。
