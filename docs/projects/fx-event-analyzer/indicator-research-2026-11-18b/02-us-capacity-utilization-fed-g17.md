## 1. 結論(先に)
- **公式の % がそのまま取れる**(系列 `CAPUTL.B50001.S` = 総合の設備稼働率、季節調整済み、単位 Percentage)。IP の前月比のような計算は要らない。
- **小さな CSV で取れる**(Fed の DDP プリセット「The Major IP and Capacity Utilization Aggregates」、約 1.4KB、直近 7 か月)。XML の zip(8.6MB)は不要。IP の指数も同じ CSV に入っているが、**IP の変化率は公式系列が無いので使わない**。
- **11/24 の年次改定**は、稼働率の**水準そのものを動かす**(設備能力を Census の調査と USGS・DOE のデータで更新、季節要因も改定)。改定の幅は事前には分からない。
- 推奨: **11/24 の改定の後で導入する**。最初に保存するのは 12/16 公表(11 月分)から。改定前の値(10 月分など)は初回値として保存しない。
- 注意: 稼働率は IP の添え物で、**単独の FX への影響は IP の変化率より小さい**。優先度は中〜低(HQ の判断)。

## 4. 取得 API・ファイル形式
| 方法 | 内容 |

| **DDP プリセット CSV(推奨)** | `https://www.federalreserve.gov/datadownload/Output.aspx?rel=G17&series=403cc340ea3a19566b30770b9e4793ab&lastobs=7&from=&to=&filetype=csv&label=include&layout=seriesrow&type=package`。鍵なし、1.4KB、`Unique Identifier` 列で系列を特定できる。2026-11-18 に取得して全値を確認 |

- **リスク**: プリセットの `series=` の値(32 桁のハッシュ)は、Choose ページが出す値。**固定のままかは未確認**(Fed が内部で変える可能性)。対策: 取得時に、ハッシュを使い、列 `Unique Identifier` が `G17/CAPUTL/CAPUTL.B50001.S` であることと単位 Percentage を**照合**し、一致しなければ保存しない。ハッシュが無効になったときは、zip に切り替えるか、Choose ページから取り直す。
- DDP の応答に、**更新日の情報は無い**(`Last-Modified` は配信の時刻)。公表日の照合は、公表予定の表(Fed の日程)と、**CSV の最後の月が対象月と一致すること**で代用する。

## 5. 改定履歴と改定頻度(現状)
- **通常の改定**: 毎回、直前の数か月が改定される。今回の発表の表(Previous estimates の行)で、**直前の公表(10/16)から 11/17 の間に、8 月が 76.4 → 76.3、9 月が 76.9 → 76.8 に動いた**(いずれも -0.1)。
- DDP は**最新版だけ**で、過去の版は取れない。FRED/ALFRED は規約上、保存できない(先の調査)。したがって、**初回値は自分で保存し、後の値は `event_revisions` に記録する**既存の方針が必要(公式から過去の版は復元できない)。
- **年次改定**(下の節)は、通常の改定より大きい。

## 6. 11/24 の年次改定と、改定前後の数値の扱い
**Fed の告知(公表ページ、2026-11-18 に確認)**
- 2026-11-24 に IP と稼働率の年次改定を行う。IP の基準年は **2022**(現在は 2017=100)。
- IP: Census の 2023・2024 年の年次データ、鉱業のデータ、季節要因を改定。推計の方法の変更もありうる。「方法の変更は **1972 年から現在までの指数**に影響する」。
- **稼働率・設備能力**: Census の四半期の設備稼働調査(2025 年第 4 四半期まで)、USGS・DOE などの新しい設備能力のデータを取り込む。
**調べたこと・調べられないこと**
- 改定の**幅は事前には不明**。過去の年次改定の幅は、今回は確認できなかった(DDP は最新版のみ、過去の改定の公表ページは読んでいない)。
- 改定前の値を、**比較の基準として保存**した(下表)。11/24 以降に同じ取得をして差を取れば、今回の改定の実際の幅が分かる。

**取り扱いの設計案**
1. **11/24 より前に導入しない**。導入が改定の後なら、最初の初回値は 12/16(11 月分)で、すべて**改定後の基準**になる。改定をまたいだ初回値の混在が起きない。
2. 万一 11/24 より前に導入する場合: 10 月分(11/17 公表)を初回値として保存しても、11/24 に動く。45 日の改定確認で `event_revisions` に入るが、**年次改定の幅は通常の改定(±0.1)と性質が違う**ので、改定の理由(年次改定)を区別できるように注記(`reason` など、DB の変更の要否を別途判断)するか、**11/24 の分は記録しない**運用にする。HQ の判断。
3. **過去比較用の履歴**(前回値・12 か月の推移)は、**改定後の DDP から一括で取り込む**(混在させない)。改定前の履歴は使わない。
4. 年次改定の日(11/24)は、通常の公表日ではない。**公表予定の表に入れない**(そのイベントに初回値を付けない)。
5. 初回値と改定値の区別は、既存の方針(初回値は不変・改定は別の履歴)を使う。

## 7. 既存基盤との適合性
| 項目 | 評価 |
|---|---|
| 取得 | 新しいアダプターが必要(CSV 1 本。`Unique Identifier`・単位の照合、最後の月の照合)。既存の JSON の API とは形式が違うが、小さい |
| 公表日の照合 | API に更新日が無い。公表予定の表 + 最後の月の一致で代用(「前の回の値を今回の値として使わない」の根拠は ONS・ABS より弱い) |
| 初回値の保存・改定 | 既存の `official-values` の枠(`parseForRelease`・`valueForPeriod`)に、新しい取得元として載せられる |

| migration | 指標 1 行(US_CAPACITY_UTILIZATION、単位 %、MONTHLY)+ 通貨ペア(USDJPY・EURUSD) |
