## 1. 結論(先に)
- **「既存の e-Stat 確認ワークフローを、変更せずに実行する」だけでは、コア CPI の分類コードを確認できない**。ワークフロー(`fx-event-analyzer-estat-check.yml`)は、**総合(`cat01` = `0001`)の有無と値だけ**を確認する作りで、品目の一覧・コアの値を出さない。さらに、**この環境からは Actions を実行できない**(`gh` と認証が無く、`workflow_dispatch` を起動できない。起動は、専用ブランチ `verify/fx-estat-check` への push だけ)。
- そのため、**今回の実データでの確認は、次の 2 つに限られた**:
  1. 統計局の公開ページ(静的な HTML)で、**コア CPI の公表値を確認**(今日取得)。
  2. 既存コードに残された、**2026-11-11 の実 API での確認の記録**を引用(今日は再確認できていない)。
- **分類コード `0161`・取得可否は、「既存コードの記録に依拠(未再確認)」**。確定させるには、**ワークフローの読み取り専用の拡張(1 回限り)の承認**が要る(§6)。

## 5. 設計への含意(確認できた範囲)
- **JP_CORE_CPI** は、既存の `JP_CPI` の仕組み(`jpCpiValues`・日程表・初回値・改定の確認)に、**品目の分類(`0161`)を足すだけ**で実装できる見込み。**統計表・appId・日程が同じ**ため、API の呼び出しは、品目の違うリクエストが 1 回増えるだけ(または 1 回で `cdCat01=0001,0161` の 2 品目を取る)。
- 既存の日本 CPI(総合)と「重複するだけ」ではない。**日銀はコアを見る**ので、独立した指標の価値がある。英国の `GB_CPI`/`GB_CORE_CPI` と同じ構成。
- 注意: 2026-09 分は総合とコアが**同じ値**。ユーザーに、2 つの指標が同じ値に見える月がある(同日・同時刻の 2 イベント)。

## 6. 確認を完結させるための提案(承認が要る。読み取りのみ)
**既存のワークフローは、総合の確認だけ**で、品目の一覧を出さない。**確認を完結**させるには、次のいずれかが要る。

| 案 | 内容 | 禁止事項との関係 |
|---|---|---|
| **A(推奨)** | `verify/fx-estat-check` ブランチに、**読み取り専用の確認の手順を 1 つ追加**した版を push して実行する。内容: ①`getMetaInfo` の `cat01` から、名前に「生鮮」「エネルギー」を含む分類の `@code`・`@name` を出す ②`tab` の分類の一覧を出す(前月比の有無) ③2026 年 9 月分の `0001`・`0161` の値を取る | **ワークフローの変更に当たる**(「ワークフロー変更は禁止」)。**HQ の個別承認が要る**。appId は出力しない(既存と同じ)。DB・Secrets(Supabase)は使わない |
| B | 既存のワークフローを、変更せずに手動実行 | 総合の確認しか出ず、**今回の確認項目には足りない**(無意味) |
| C | HQ・担当者が、`appId` を持つ環境で、`getMetaInfo` を読んで、結果を共有する | 秘密情報(appId)の取り扱いは、HQ の側 |

- 案 A の追加部分(概略、Python。**まだ適用していない**):
  ```python
  # cat01 の分類のうち、名前に「生鮮」「エネルギー」を含むものの code・name だけを出す
  # tab の分類の一覧(code・name)を出す
  # getStatsData(cdTab=3, cdArea=00000, cdCat01=0001,0161, cdTime=2026000909) の値を出す
  ```
- 案 A を承認いただければ、実行の結果で、本書の「未再確認」を確定します。**承認が無い間は、本書の `0161`・取得可否は「既存コードの記録に依拠」の扱い**で、実装設計に進む場合も、**未再確認の前提**を明記します。
