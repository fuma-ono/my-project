## 0. 前提・方針

- 対象はホーム画面のアプリ層キャッシュ(`HomeCacheStore`)。HTTPレベルのキャッシュ(`URLCache`)は
  このアプリでは使われていない(別途確認済み、R23)。
- 「鮮度が切れている」ことと「情報を消す」ことは別の判断。古い情報の保持自体は否定しないが、
  最新情報と区別できることを必須とする。
- Render Freeの起動待ち対策(キャッシュの先出し表示、約20秒のコールドスタートを隠す目的)と、
  データそのものの鮮度期限は、目的が異なる別問題として扱う。前者のための先出し表示は維持する。
- 本文書は設計のみであり、数値(TTL・閾値等)は確定しない。確定はHQ判断。

## 1. 鮮度情報の責任分離(5項目)

「Backend上のデータ変更時刻(`updated_at`)が古いこと」と「Backendが取得元を確認できていないこと」
は別の問題であり、`updated_at`だけでは区別できない。5つの責任に整理する。

| 項目 | 意味 | 責任 | 役割 |
|---|---|---|---|
| `savedAt` | iOSが最後に取得完了した時刻 | iOS(既存) | 「いつ端末に保存したか」の機械的な記録。再確認期限(§3-A)判定の起点。 |
| `updated_at` | Backend上で対象データ(`actual`/`forecast`/`data_status`等)が最後に変化した時刻 | Backend(新設) | 「内容が実際に変わったか」の判定に使う。**ただし、これが古いことだけでデータを無効と判断してはならない**(変化していないだけで正しく最新の場合がある)。 |
| `checked_at` | Backendが取得元(BLS/BoC等)を最後に正常確認できた時刻(値が変わらなくても更新される) | Backend(新設) | **実際の取得元確認の鮮度はこちらで判断する**(判定方式は§2)。 |
| `revision_version`等 | 改定を識別する値(候補、§5参照) | Backend(新設・候補) | 改定が何回発生したか・最新の改定がどれかを識別する。 |
| `revision_status` | 改定の有無を示す表示用情報(`NONE`/`REVISED`、既存はEventDetail限定) | Backend(既存・拡張候補) | UI表示用の簡易フラグ。詳細は§5で限界を明記。 |

## 2. checked_atの判定方式(P1-1、Cレビュー対応)

第3版では「前回値との比較」(`checked_at`が前回より新しいか)で鮮度回復を判定していたが、
Cレビューの指摘を受け、この比較方式を**廃止**する。

### 2.1 判定方式の変更

- **廃止**: 前回保存した`checked_at`と今回取得した`checked_at`を比較する方式。
- **採用**: `now - checked_at > threshold` という**絶対時刻判定**を基本とする。
  現在時刻から`checked_at`までの経過時間だけで「確認が古いか」を判定し、前回値の記憶・比較は行わない。
  (閾値`threshold`の数値は決定しない。HQ判断待ち。)

### 2.2 Backendの確認周期より短い間隔で取得しても誤警告しないこと

iOS側の再取得間隔(§3-Aの再確認期限)がBackendの実際の確認周期より短い場合(例: iOSが5分おきに
再取得しても、Backend側の取得元確認は30分おきにしか行われない)、`checked_at`が更新されていない
ことは異常ではない。これを誤って「確認停止」と警告しないため:

- `threshold`は、Backend側の取得元確認の実際の周期より**十分大きい値**として設計する
  (運用上の要件として明記。具体的な周期・閾値の数値関係はHQ判断)。
- 絶対時刻判定(2.1)自体が「前回との差分」を見ないため、iOSが何度再取得しても`checked_at`が
  同じ値のままであること自体は誤警告の原因にならない(`now - checked_at`が`threshold`を
  超えていない限り、何度再取得しても「鮮度OK」のまま一貫する)。

### 2.3 取得元確認が不要な確定済みイベントの扱い

Backend側の運用として、ある指標・ある発表が「もう取得元を再確認する必要がない」と判断された
場合(例: 最終確定から十分な時間が経過し、Backend自身がそのイベントの取得元確認を終了している)、
`checked_at`の更新が止まることは異常ではなく正常である。これを「確認停止」と誤判定しないため、
**`checked_at`ベースの鮮度判定を適用する対象を「取得元確認が継続して行われるべきイベント」に
限定する**という除外ルールを設ける。具体的な判定基準(どのイベントが「取得元確認不要」に
該当するか)はBackend側が決める必要があり、候補としてはBackendが新設フィールド(例:
`checked_at`が`null`の場合は「確認対象外」として鮮度判定自体をスキップする)で示す方式がある。

### 2.4 「確認不要」と「無効化・再取得の要件」は分離する

確定済み(取得元確認が不要と判定された)イベントであっても、**訂正・取消の可能性はゼロではない**
(BoCの事後訂正など)。したがって:

- `checked_at`ベースの鮮度判定(取得元確認が継続しているか)は確定済みイベントに対して免除してよい。
- しかし、**再確認期限(§3-A)および無効化・取消の検知(§8)は、確定済みイベントにも引き続き
  適用する**。この2つは別の軸であり、「確認不要」が「二度と再取得しない」を意味しないことを
  明記する。

### 2.5 端末時計とサーバー時計のズレへの対応

`now`はiOSのローカル時計基準、`checked_at`はBackend(サーバー)時計基準であるため、両者の時計が
ズレている場合、`now - checked_at`の差分が実際より長く/短く計算される可能性がある。対応候補
(未確定):

| 候補 | 内容 | 長所 | 短所 |
|---|---|---|---|
| (a) サーバー時刻オフセット補正 | Backendのレスポンス(HTTPヘッダまたは専用フィールド)でサーバー時刻を返し、iOS側で`ローカルnow - server_time`のオフセットを算出して`checked_at`比較時に補正する | 時計ズレの影響を正確に除去できる | API拡張・実装コストが増える |
| (b) 閾値マージンで吸収 | オフセット補正をせず、`threshold`に通常想定される時計ズレ(数秒〜数分程度)分のマージンを持たせる | 実装が簡単 | 精度が粗く、極端な時計ズレは吸収できない |

### 2.6 サーバー時刻を取得できない場合の扱い(候補)

(a)のオフセット補正ができない場合の候補(未確定):

- (i) 補正なしで`checked_at`の絶対値をそのまま使う((b)と同じ扱いにフォールバック)
- (ii) サーバー時刻が取得できないレスポンスでは`checked_at`判定自体を一時的にスキップし、
  `savedAt`ベースの再確認期限(§3-A)のみで代替する

いずれも未確定。閾値・採用方式はHQ判断待ち。

## 3. TTLの階層再整理(P1-2、Cレビュー対応)

第3版では「全体TTL」と「dataStatus別TTL」を単一の`min()`で統合していたが、これは
**「再取得を試みるタイミング」**と**「古い情報を画面に残してよい上限」**という異なる役割を
混同していた。第4版では3つの概念に分離する。

### 3-A. 再確認期限(Re-check Deadline)

「Backendへ再取得を試みるべき期限」。経過すると自動再検証(§3の既存設計、フォアグラウンド復帰等)
のトリガーになり得るが、これ自体は「表示を変える」ものではない。

| 対象 | 候補(未確定) |
|---|---|
| DATA_PENDING / NOT_ANALYZABLE | 5〜15分 |
| READY | 数時間(無期限は避ける) |
| 訂正リスクのあるデータ(政策金利等) | 上記よりさらに短い候補(例:15分) |

### 3-B. 最大表示期限(Max Display Deadline)

「古いデータを画面に残してよい絶対的な上限」。イベント種別に関わらず共通の上限として扱う。

- オンラインでこれを超えた場合: 値は消さずに「情報が古くなっています」の強い警告(維持)。
- オフラインでこれを超えた場合: 値は残すが「オフラインのため確認できません」+「古い情報」の
  両方を明示。さらに長時間オフラインが続いた場合(最大表示期限の数倍等、未確定)に、
  値を非表示にするか・より強い警告に切り替えるかは段階的エスカレーション案を候補とし、
  具体的な境界はHQ判断。
- 最大表示期限を超えた場合の表示/非表示/警告の扱い: 「警告 → 強い警告 → 非表示」の段階的
  エスカレーションを候補として提示する。数値・段階数は未確定。

### 3-C. FX価格期限

既存の30分ルール(`HomeCacheStore.priceMaxAge`)を**そのまま維持**。イベント情報(A・B)とは
**完全に独立**して判定する(通貨ペア価格だけに適用される別軸)。

### 3.1 min()の適用対象の再設計

第3版の誤り: 「全体TTL」(=B相当)と「dataStatus別TTL」(=A相当)を同じ`min()`に入れて
1つの`effective_ttl`としていたため、AとBの役割の違いが表現できていなかった。

第4版の整理:

```
reCheckDeadline(event) = min(3-Aの該当候補: DATA_PENDING/NOT_ANALYZABLEまたはREADY, 訂正リスク候補(該当時))
  → 「再取得を試みるタイミング」の基準。min()はA内部の複数候補同士にのみ適用する。

maxDisplayDeadline(event) = 3-B(全体の最大表示期限)
  → イベント種別に関わらず共通。「画面に残してよい上限」の基準。AとBの間にはmin()を適用しない
    (AとBは役割が異なる独立した軸であり、優劣ではなく併存する)。

FX価格: 3-C(30分)は上記と無関係に独立判定。
```

**READYの再確認期限(A)を数時間にする場合との整合**: Aの「READY=数時間」はあくまで
「次に再取得を試みるまでの猶予」であり、Bの「最大表示期限」(全体共通、より短い可能性がある)
を上書きするものではない。たとえばREADYの再確認期限が3時間でも、最大表示期限(B)が1時間なら、
再確認期限が来る前にBによる「古い情報」警告が先に表示される。逆に、再確認期限(A)が来て
再取得を試みても失敗し続けている場合は、既存の`refreshFailed`表示とBの最大表示期限判定が
組み合わさって、最終的に表示継続/エスカレーションが決まる。AとBは矛盾する関係ではなく、
**Aは「いつ動くか」、Bは「いつまで見せてよいか」という異なる質問に答える**、という整理である。

## 4. Backendとの責任分担

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. iOSのTTLだけで管理 | 経過時間のみで鮮度判定 | Backend変更不要、既存API互換の心配なし | Backendの内容変化・確認状況を一切検知できない |
| B(推奨). Backendの`updated_at`/`checked_at`/`revision_version`とiOSのTTLを併用 | §3Aの再確認期限は「再取得のタイミング制御」、実際の鮮度・健全性判定は§2の`checked_at`絶対時刻判定で行う | Backendの実際の状態を検知可能 | Backend API拡張が必要 |

**検知できる範囲**: Backend DB上で`actual`/`forecast`/`data_status`/改定が実際に変わったケース、
および`checked_at`があればBackendが取得元の確認自体を継続できているか。

**検知できない(B案でも)**:
- Backendの取得元確認プロセス自体にバグがあり、`checked_at`を誤って更新し続ける場合(値は
  変わっていないのに確認時刻だけ進む「見せかけの健全性」)。iOS側では検知不能であり、
  **取得元確認が停止・遅延した場合の検知と表示責任はBackend側にある**(§13のPASS条件に明記)。
- revisionが値を変えずにフラグだけ変える、あるいは逆に値を変えてもフラグを更新しない実装ミスが
  Backend側にあった場合。これもiOS側では検知不能。

**追加フィールド案(Backend API変更、未実装・案のみ)**:
`checked_at`・`updated_at`・`revision_status`(Home向け拡張)・`revision_version`相当の値を
`GET /home`の`events[]`等に追加。**既存APIとの互換性**: いずれも新規の**optionalフィールド**
として追加する前提であれば、JSONDecoderは未知キーを無視するため古いアプリ・古いBackendとの
互換性は保たれる(`resultType`/`valueDecimals`と同様のパターン)。

## 5. 改定の識別 — revision_statusの限界

既存の`revision_status`(`NONE`/`REVISED`、api-design.md 770-775行目、`EventRevision`の存在有無から
Backendが動的算出)は、**「改定が1件以上あるか」の二値情報でしかなく、REVISED後に再度改定が
発生した場合(2回目・3回目の改定)を識別できない**。

**複数回の改定を識別するための候補**(採用値は未確定):

| 候補 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 最新`revision_id` | 最後に適用された改定行のID(`GET /events/{id}/revisions`の`revision_id`) | 既存のテーブル構造をそのまま使える | IDが連番でない場合、「新しいか古いか」の比較に使えない可能性 |
| `revision.created_at`(最新) | 最新の改定行の`created_at`(既存、api-design.md 999-1026行目) | 既存フィールドの転用で済む | 時刻比較のみで「何回改定されたか」は分からない |
| `revision_version`(新設・改定回数のカウンタ) | `event_id`ごとの改定件数、または単調増加するバージョン番号 | 「前回確認時より増えたか」で再改定を確実に検知できる | Backend側での新規実装(カウンタ管理)が必要 |

## 6. ロック情報の漏洩対策(P2-1、Cレビュー対応)

FREE/PROのロック(`locked: true`)状態で、新設フィールド(`checked_at`/`updated_at`/
`revision_version`等)をそのまま返すと、ロックされているはずの情報(改定の有無・頻度・直近の
更新タイミング)が、値そのものをロック解除せずに推測できてしまう可能性がある。

**既存の整合性**: 既存の`revision_status`は、ロックされた発表では固定値`"NONE"`を返す設計
(api-design.md 743行目、v1.33「古いアプリとの互換」)。同様に`previous_locked`も、隠すべき
情報(前回値)を`null`にする設計。新設フィールドもこの既存パターンに合わせる。

**禁止事項(明記)**:
- ロックされた発表の`checked_at`/`updated_at`に実際の値をそのまま返してはならない
  (更新頻度・直近の訂正タイミングから、ロックを外さずに「直近で何か動きがあった」ことが
  推測できてしまうため)。
- ロックされた発表の`revision_version`/改定件数をそのまま返してはならない(改定が何回起きたか
  という情報自体がロック中の発表の「動き」を明らかにしてしまうため)。
- ロック解除の前後で、隠していた値と解除後の値の差分からロック期間中に何が起きたかを
  逆算できるような実装にしてはならない。

**実装方式(未確定、候補のみ)**: 既存の`revision_status`固定値`"NONE"`パターンに倣い、
ロック中は`checked_at`/`updated_at`を固定値(例:`null`、またはロックと無関係な値)で返す、
`revision_version`も固定値(例:`0`または`null`)で返す。採用方式はHQ判断待ち。

## 7. キャッシュ保存・比較仕様(P2-2、Cレビュー対応)

- **比較単位**: イベント単位を基本候補とする(スナップショット全体ではなく、`events[]`の
  各行ごとに`checked_at`/`revision_version`等を比較する)。
- **保存とのタイミング**: 現在の`HomeCacheStore.save(response:...)`は前回のスナップショットを
  読み込み(`stored()`)、お気に入りだけを引き継いで丸ごと新しいスナップショットに置き換える。
  新フィールドの比較(「改定が増えたか」等)には、**置換前に旧スナップショットの該当イベントを
  探し出し、新しい値と比較するロジックが必要**(`favorites`引き継ぎと同じ位置に、イベント単位の
  比較ロジックを追加するイメージ)。
- **「改定あり」表示をいつ消すか**(候補、未確定):
  - (a) ユーザーがその発表の詳細画面を開いて確認した時点で消す
  - (b) 次の正常な再取得で比較結果が「前回確認時と同じ」になった時点で消す
  - (c) 一定期間表示したら自動的に消す
- **新フィールドを持たない既存キャッシュの扱い**: 旧フォーマットのキャッシュ(新フィールド追加前
  に保存されたもの)は新フィールドがすべて`nil`相当になり、比較ができない。「鮮度情報なし」として
  扱い、§3-A/Bの判定に使えないため、安全側として「鮮度不明=警告を出す」か「表示は継続する」かは
  HQ判断。
- **`currentFormatVersion`の更新要否**: 新フィールドをoptionalとして追加するだけであれば、
  Swiftの`Codable`は新規optionalプロパティの追加に対して後方互換(古い保存データの読み込み時に
  単に`nil`になるだけで失敗しない)。したがって**版を上げる必須性はない**と考えられるが、
  比較ロジックの前提が変わる等の運用上の理由があれば版を分ける判断もあり得る。要否はHQ判断。
- **`userID`不一致時の既存`clear()`処理との整合性**: 既存の`load(for:)`・
  `discardIfPlanDiffers(...)`における`userID`不一致時の`clear()`ロジックは、新フィールド追加後も
  変更不要(ユーザーが変わればスナップショット全体を消すという既存方針と、新フィールドの追加は
  独立した話であり矛盾しない)。

## 8. 取消・無効化・巻き戻し(P2-3、R18の重要要件として追加)

前版にはこの観点が欠けていた。R18の要件として明記する。

- 再取得成功時、以下を正しく反映できる設計にする:
  - **行の欠落**: そのイベントがもう`/home`の応答に含まれない(日付が変わった、対象外になった等)
  - **状態後退**: 一度`RELEASED`になっていたイベントが別の状態に戻るような異常系
    (通常は起こらないはずだが、Backend側の不整合に対する防御として扱う)
  - **`CANCELLED`**(取消)への変化
  - **`INVALIDATE`/`ROLLBACK`相当の変化**: Backend側で一度確定した値を取り消す/巻き戻す操作
    (既存APIには明示的なENUMが無いため、Backend拡張の候補として扱う)
- **古い値を新しい値として残さない**: 再取得が成功した場合、原則としてスナップショット全体を
  新しい応答で置き換える(既存の`save()`の設計を維持)。万一再取得が「部分的に古い情報を含む」
  応答を返すような実装ミスがBackend側にあった場合、iOS側では検知できない(§4と同じ限界)。
- **オフライン時に無効化された可能性のある情報を表示し続ける上限**: §3-Bの「最大表示期限」を、
  取消・無効化のリスクがあるイベントにも適用する。最大表示時間を超えた場合の挙動(候補):
  - 値を表示から完全に隠す
  - 「この情報は取消・変更されている可能性があります」という警告に差し替える
  採用方式・具体的な時間数値はHQ判断待ち。
- **テスト観点(追加)**:
  - 再取得成功時、前回存在したイベントが応答から消えた場合に、キャッシュ上の該当行が正しく
    除去されること
  - `status`が`CANCELLED`に変化した場合に、古い`SCHEDULED`/`RELEASED`表示が残らないこと
  - オフラインで最大表示期限を超えた場合に、設計通りの表示(非表示/警告差し替え)になること

## 9. Backendの確認状態(P2-4、Cレビュー対応)

Backendが取得元を確認できているかをiOSが判断できるようにする。既存の`HomeSpeechesStatus`
(`windowDays`/`lastSuccessAt`/`stale`、`FXEventAnalyzer/Features/Home/HomeModels.swift`)を
参考候補とする。

- **Backendが返す確認状態フィールドの候補**:
  - `checked_at`(既出、最後に正常確認できた時刻)
  - `stale`(真偽値、既存の`HomeSpeechesStatus.stale`と同形。「取得できていない」ことを明示)
  - `last_success_at`(既存の`HomeSpeechesStatus.lastSuccessAt`と同形)
  既存の`HomeSpeechesStatus`がまさに同種の構造を持っており、これを参考に指標側にも同様の構造
  (例:`IndicatorCheckStatus { lastSuccessAt, stale }`的な型)を追加する案が既存パターンとの
  整合性が最も高い。
- **`stale`判定の責任主体**: Backend側(取得失敗・遅延の実際の検知はBackendのIngestion Worker
  が行い、iOSは判定結果を受け取って表示するだけ)。
- **取得失敗・確認遅延・確認停止の区別**: 意味が異なる概念であり、単一の`stale`真偽値だけでは
  区別できない可能性がある。
  - 取得失敗: 直近の確認試行自体がエラーで終わった(一時的である可能性が高い)
  - 確認遅延: 確認は行われているが、予定より遅れている(軽微)
  - 確認停止: 確認プロセス自体が長期間動いていない(深刻)
  区別が必要な場合は、単純な`stale`真偽値ではなく`checked_at`の経過時間(§2)と組み合わせて
  段階的に判定する必要がある。
- **iOS側の表示責任**: Backendから受け取った`checked_at`/`stale`等を基に、§3-A/Bのロジックで
  表示を決定する。確認プロセスの健全性そのものを検証する手段はiOS側にはない。
- **`checked_at`だけで判断する場合の限界**: 経過時間だけでは「確認が単に遅れている」のか
  「確認プロセスが完全に停止している」のかを区別できない(どちらも「`checked_at`が古い」という
  同じ症状になる)。より詳細な区別が必要な場合は、Backend側で専用の`stale`フラグやエラー状態を
  別途提供する必要がある。API仕様は提案段階とし、実装はしない。

## 10. StrategyAnalysis(分析機能)への影響

`StrategyAnalysisViewModel.swift:39-46`は`HomeCacheStore`を一切参照せず、独自に
`apiClient.send(endpoint)`で`StrategyAnalysisResponse`を直接取得する設計である。
**HomeCacheStoreから独立していることは確認済みであり、この点は維持する。**

ただし、「Homeキャッシュの鮮度ロジックと無関係」であることと「鮮度の問題が一切ない」ことは
同じではない。StrategyAnalysisは都度Backendへ直接問い合わせるため、**Backendが古いデータ
(取得元確認が停止している等)を返した場合、StrategyAnalysisも同じ古い値をそのまま表示する**。

- **記述**: StrategyAnalysisはHomeCacheStoreのTTL・鮮度ロジックには依存しないが、Backendが
  返すデータそのものの鮮度(`checked_at`等)には同じく影響を受ける。分析結果が実際にはどの
  時点のBackendデータに基づくものかを利用者に示す手段が、現状のAPIには無い。
- **分析APIの設計拡張(案)**: `StrategyAnalysisResponse`にも、§1・§4で提案した`checked_at`/
  `updated_at`相当のフィールドを(必要な範囲で)含められるようにし、分析結果の横に
  「この分析はHH:mm時点のデータに基づきます」等の注記を表示できる設計にしておく。
  これはHome側のキャッシュ鮮度とは別個の仕組みとして、分析API側に必要なら個別に追加する。

## 11. 表示・分析利用の制御

| 状態 | Home画面 | StrategyAnalysis(分析画面) |
|---|---|---|
| オンラインで最大表示期限切れ(§3-B) | 値は維持し「情報が古くなっています・更新中」、裏で再取得 | 取得した`checked_at`が古ければ§10の注記を表示 |
| オフラインで最大表示期限切れ | 値は維持し「オフラインのため更新できません(HH:mm時点)」の強い警告、さらに長時間オフラインならエスカレーション(§3-B) | 新規取得不可、既存のネットワークエラー表示 |
| READYだが`checked_at`が古い(確認停止・遅延の可能性) | 「確定済みですが確認が古い可能性があります」等の中間的注意 | 同様の注記を検討(§10) |
| revisionが変わった(複数回含む、§5) | 該当行に「改定あり」マーク、複数回改定は`revision_version`等で検知できた場合のみ区別表示 | 分析結果が改定前のデータに基づく場合は再実行を促す注記を検討 |
| `CANCELLED`/無効化・巻き戻し(§8) | 古い`SCHEDULED`/`RELEASED`表示を残さず反映、オフライン時は最大表示期限で扱いを切替 | 分析結果が取消済みデータに基づく場合は再実行を促す注記を検討 |
| ロック中の発表(§6) | `checked_at`/`updated_at`/`revision_version`は固定値を返し、鮮度表示もロック表示を優先(値の「動き」を推測させない) | ロック中の発表は既存のPLAN_LIMIT_EXCEEDED等の扱いを維持 |
| 取得失敗が継続 | 既存`refreshFailed`を維持、継続時間に応じ警告を段階的に強める | 都度のエラー表示のみ(キャッシュ非依存のため「継続」という概念がない) |

## 12. 軽微な整合性整理(P3)

C review原文のP3-1〜P3-4の項目名はこの指示に含まれていないため、本版では以下を「整理が必要と
考えられる軽微な項目」として扱う。項目名が実際のC指摘と一致しない可能性がある点は§15の
未解決事項に明記する。

- **SCHEDULEDの発表時刻経過後の既存除外ロジックと新TTLの関係**(本指示で明記を求められた項目):
  既存の`HomeCacheSnapshot.displayEvents(now:)`は「`status == .scheduled && releaseDatetime <= now`」
  のイベントをキャッシュ表示から除外する。これは「予定のまま時刻だけ過ぎた」古い表示を隠すための
  既存ロジックであり、新設する§3のTTL(再確認期限・最大表示期限)とは適用対象が異なる:
  `displayEvents`の除外は「このイベント行自体を表示しない」という二値のフィルタであり、TTLは
  「表示するが鮮度が切れている旨を警告する」という別軸の処理。両者は**競合しない**
  (`displayEvents`のフィルタが先に適用され、残ったイベントに対して§3のTTL判定が適用される、
  という順序関係として整理する)。
- **FX価格の既存30分ルールとTTL階層の表記整合**: §3-Cとして明示的に分離したことで、イベント本体
  の階層(A/B)と混同しないようにした(本版で対応済み)。
- **バナー文言(`HomeRefreshNoticeText`)の拡張に伴う既存文言との後方互換**: 新設する警告段階
  (§3-B)を追加する場合、既存の`.showingCache`/`.refreshFailed`の2文言に新しい文言(例:
  「確認が古い」「取消の可能性」等)が追加される。既存の2文言の意味・表示条件は変更しない。
- **本設計書自体の改訂履歴管理**: §16に改訂履歴を追加した。
