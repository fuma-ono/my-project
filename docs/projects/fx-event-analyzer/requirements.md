## 0. 本書の目的

本書は、FX市場における経済指標・金融政策・要人発言などの「市場イベント」に対して、

市場予想 → 実際の結果 → 予想との差(サプライズ) → なぜ差が発生したか → 為替が実際にどう動いたか

を一連の流れで確認・分析できるFXイベント分析アプリを開発するための要件定義書である。

本アプリはFX価格の将来予測や自動売買を目的としない。

---

## 1. プロダクトコンセプト

コアコンセプト:

「予想と結果、その結果による相場の反応を一画面で理解する」

ユーザーが経済指標発表を見た際に、「結果が予想より強かった/弱かった」だけではなく、

- どの程度予想から離れたのか
- なぜその結果になったのか
- その結果、為替が何分後に何pips動いたのか
- 過去にも同じような結果で同じように動いたのか

まで確認できることを価値とする。

## 2. 対象ユーザー

- FXトレーダー
- 経済指標を重視する投資家
- FX市場を学習しているユーザー
- 経済ニュースと為替の関係を分析したいユーザー

## 3. MVPの目的

MVPでは以下を実現する。

1. 重要経済指標を確認できる
2. 市場予想・実績・前回値を確認できる(**発表時点のスナップショットとして**)
3. 予想と実績の差(Surprise)を確認できる
4. 実績が予想から乖離した背景を、**公式情報・信頼できる情報源への出典付きで**確認できる(自由生成AIによる推測解説はMVP対象外。詳細は12章)
5. 指標発表前後のFX価格変動を確認できる
6. 1分・5分・15分・30分・60分後の値動きを確認できる
7. 過去の同一指標イベントを比較できる(データ品質の揃った件数のみ)
8. 過去イベントの統計を確認できる
9. サプライズと為替変動の関係を確認できる(符号ベース)
10. 過去イベント詳細から、その指標自体の詳細画面へ遷移できる

## 4. 経済指標

### 4.1 初期対応指標

**米国**: FOMC / Nonfarm Payrolls(NFP) / CPI / PPI / PCE / GDP / ISM Manufacturing / ISM Services / Retail Sales / ADP Employment / Initial Jobless Claims

**日本**: BOJ政策金利 / BOJ金融政策決定会合 / CPI / GDP / 雇用関連指標

**欧州**: ECB政策金利 / ECB総裁記者会見 / CPI / GDP / PMI

**イギリス**: BOE政策金利 / CPI / GDP / 雇用関連指標

**その他**: オーストラリア・ニュージーランド・カナダ・スイス・その他主要国の主要指標を取得可能な設計とする。

### 4.2 指標ごとの発表頻度と必要な履歴期間

指標は発表頻度が大きく異なる(月次: CPI・雇用統計等 / 四半期: GDP等 / 不定期: FOMC・要人発言等)。

**要件として、「過去イベント比較」に必要な最低件数(目安: 直近20件相当)を確保するために必要な履歴年数を、指標の発表頻度ごとに定義する。** 四半期指標(GDP等)で20件を確保するには5年分の履歴が必要であり、月次指標より長い取得期間が必要になることを、API選定・データ保持方針の評価基準に含める(6.3節参照)。

## 5. 経済イベントデータ

### 5.1 基本方針: Snapshot(発表時点の値)とRevision(後日の改定)を区別する

経済指標は発表後に何度も改定される(NFPは翌月・翌々月に改定、GDPは確定値への改定、CPIは季節調整の見直し等)。本アプリは、以下の2つの概念を明確に区別することを要件とする。

- **EventSnapshot**: そのイベントが発表された**その時点**で、市場・ユーザーが実際に見ていた値(Forecast / Actual / Previous)。**不変**(後から書き換えない)。
- **EventRevision**: 発表後に判明した改定値の履歴。いつ・どの値が・どのソースにより改定されたかを記録する参考情報。

**最重要原則: 市場反応の分析(Surprise計算・pips計算・過去比較・統計)は、常にEventSnapshotの値を用いる。後日の改定値によって、過去のSurpriseや市場反応を再計算してはならない。** 相場は発表当時に発表された値に反応するのであり、数ヶ月後の改定値には反応しないため。

改定情報自体は、ユーザーに「その後この指標は◯◯に改定されました」という参考情報として提示してよいが、これは分析結果を書き換える目的ではなく、事実の補足情報として扱う。**改定値を画面に表示する場合は、必ず「改定後」等のラベルを付し、発表時点(Snapshot)の値と文言上・視覚上も明確に区別すること**(HQ回答、2026-09)。機能一覧(features.md)のFEAT-045「Revised Previous表示」は、この改定履歴(EventRevision)ベースの参考表示を指し、EventSnapshotに改定後の値で上書きする可変フィールドを持たせることは意味しない(DB詳細設計でEconomicEventとEventSnapshotを別Entityとして分離したことに伴い、v1.4で記述を更新)。

### 5.2 管理データ

各イベント(Snapshot)について、最低限以下を管理する。

- event_id
- indicator_id
- event_name
- country
- currency
- release_datetime(スケジュール時刻。5.3節で精度を扱う)
- importance
- forecast(存在しない場合はnull。9章参照)
- actual(発表時点の値)
- previous(発表時点で表示されていた前回値)
- unit
- description
- source
- data_status(6章のデータ品質状態)

改定履歴(EventRevision)には、少なくとも以下を管理する。

- どの値が(actual/previousのいずれか)
- 改定前の値・改定後の値
- 改定が判明した日時
- 改定情報のソース

可能であれば、consensus・release_url・データ取得時刻・データ更新時刻も保持する。

### 5.3 release_datetimeの精度

経済指標APIが返す`release_datetime`は、提供元によって分単位までの場合と、それより粗い場合がある。**取得した`release_datetime`がどの精度で確定しているかを示すフラグを保持する**(例: 分単位で確定/概算のみ)。詳細な同期ルールは8章・9章参照。

## 6. データ取得方針

### 6.1 API選定の必須条件

経済指標APIについては、開発時点で最適なサービスを調査・選定する。

**選定にあたり、以下を必須条件とする(いずれか一つでも満たさない場合は採用しない):**

1. Forecast / Actual / Previous / Revision情報を取得できること
2. 商用利用が許諾されていること
3. **取得したデータを、月額課金制のエンドユーザー向けアプリの画面に表示・配信する権利(再配布権)が契約に含まれること。** 「APIを呼び出せること」と「そのデータを有料ユーザーに見せられること」は別の権利であり、混同しない。
4. データの保存(DB保存)が許諾されていること

### 6.2 候補と現時点のライセンス確認状況

**以下はいずれも「要確認」であり、確定情報ではない。最終選定は詳細設計に進む前に、各社へ直接見積もり・利用規約の確認を行った上で決定する。**

| API | 商用配信権 | 備考(2026-09時点、要再確認) |
|---|---|---|
| Trading Economics | 要確認(標準プランには含まれず、配信権はEnterprise個別契約の可能性が高い) | 経済指標カレンダーAPIあり。標準プラン料金とEnterprise料金は別 |
| EODHD | 要確認(個人プランでは商用配信不可、B2Bプランが必要な可能性が高い) | 経済指標データの取得開始時期が比較的新しい可能性があり、低頻度指標(GDP等)に必要な履歴年数を満たすか要確認 |
| Investing.com | 要確認(公式APIの有無を含め要確認) | 非公式スクレイピングを本番データ取得方式として採用しない(6.4節) |

上記の「要確認」「未評価」は、推測で埋めずに詳細設計着手前に事業者へ直接確認することを要件とする。1社に固定する必要はなく、経済指標と価格で異なるAPIを組み合わせてよい。

### 6.3 API選定の総合評価基準

価格だけでなく、以下を総合的に評価する。

1. Forecast / Actual / Previous / Revision
2. Historical data(4.2節で定義した、指標頻度ごとに必要な履歴年数を満たすか)
3. Release timestamp(精度)
4. Country coverage / Event coverage
5. **商用利用・エンドユーザー配信・データ保存の可否(必須条件、6.1節)**
6. Rate Limit
7. API料金(配信権込みの実質コスト)
8. 将来的な拡張性

### 6.4 Investing.com / Forex Factory の扱い

データ項目・画面構成・情報量の参考対象とする。ただし非公式スクレイピングを本番の主要データ取得方式として前提にしない。

## 8. FX価格データ

**MVP**: 1分足・5分足・15分足・30分足・1時間足
**将来**: 4時間足・日足

価格データには最低限、timestamp・pair・open・high・low・closeを保持する。volumeはFX市場では意味が提供元により異なるため必須項目としない。

### 8.1 通常時とイベント前後での取得方式の区別

- **通常時**: 経済指標カレンダーは定期取得(バッチ)でよい。
- **イベント前後**: 重要イベントの発表前後は、価格データを優先的に、より高頻度に取得する。**具体的な取得間隔(秒単位)やストリーミング利用の要否は、採用するFX価格APIのRate Limit・ストリーミング対応状況を確認した上で詳細設計で決定する。** 本書では「イベント近辺では高頻度取得またはストリーミングを利用する」という方針までを要件とする。

## 9. イベント発表前後の値動き

### 9.1 基準時刻の定義

- DB内部の時刻は**UTCで統一**する。ユーザーへの表示時にユーザーのtimezoneへ変換する。
- 経済指標APIの`release_datetime`を基準時刻(T)とする。
- **1分足はopen timestamp基準で統一する**(足の開始時刻をその足の時刻とみなす)。
- **発表直前価格の定義**: Tを含む1分足の直前に確定した1分足のClose価格とする。
- **T+1m / T+5m / T+15m / T+30m / T+60mの定義**: Tの時刻からそれぞれの分数が経過した時点までに確定している1分足のCloseを用いる。
- 利用するFX価格APIのtimestamp仕様(足の開始/終了どちら基準か)をデータソースごとに個別に確認し、上記の定義に正規化してから保存する。

### 9.2 スケジュール時刻と実発表時刻の扱い

経済指標の実際の発表時刻は、スケジュールされた時刻から数分ずれることがある(要人発言の延着、指標のembargo break等)。

**本バージョンでは、実発表時刻を価格変動から自動推定する仕様は確定しない。** 実発表時刻を外部ソースから直接取得できない場合は、**スケジュール時刻(release_datetime)を基準時刻として採用し、その旨を時刻精度フラグ・データ品質フラグとして保持する**。秒単位での実発表時刻検出アルゴリズムは詳細設計で検討する。

### 9.3 変動計算

各時点(発表直前・+1m・+5m・+15m・+30m・+60m)について、price・change(絶対値)・change_pips・change_percentを計算する。計算はBackend側を正とする(10章)。

例:
```
USD/JPY
Before  147.20
+1m     147.48 (+28 pips)
+5m     147.76 (+56 pips)
+15m    148.05 (+85 pips)
```

### 9.4 データ欠損・不確実性

以下の場合、データ品質状態を保持する(欠損値を推測で埋めない)。

- 価格データ欠損
- イベント時刻不明・精度が低い
- API障害・取得遅延
- 時刻ずれの疑い
- 市場休場

`data_status`として管理し、UIでは`N/A`または「データ不十分」と表示する。推測値は生成しない。

## 11. サプライズ分析(MVP: 符号ベース)

### 11.1 基本計算

原則: `Surprise = Actual - Forecast`

ただし、指標ごとに「高い方が市場にとって好ましい」「低い方が好ましい」「単純比較できない」が異なるため、**Indicatorごとに方向性(favorable_direction: higher_is_favorable / lower_is_favorable / not_applicable)を設定できる構造とする。**

MVPでは、この方向性を用いた**符号ベースの判定(上振れ/下振れ/予想通り)**までを実装対象とする。

### 11.2 Forecastが存在しない場合

要人発言や一部の指標では、市場予想(Forecast)自体が存在しない、または複数のコンセンサス値が乱立することがある。

**Forecastが存在しないイベントは`surprise = null`とする。0として扱ってはならない。** UIでは「Surprise分析対象外」等の状態を明示する。

### 11.3 将来拡張

以下はMVP対象外、将来拡張とする。

- Absolute Surprise / Percentage Surprise / Standardized Surprise
- Surprise Magnitude Bucket(段階的分類)
- 類似Surprise分析

## 12. 指標が予想から乖離した理由(MVP: 出典付き事実要約に縮小)

### 12.1 目的

ActualがForecastから乖離した場合、なぜその結果になったのかをユーザーが理解できるようにする。

### 12.2 MVPスコープ

**MVPでは、この機能を「公式発表・公式資料・信頼できる情報源からの、出典URL付きの事実要約」に限定する。** 自由生成AIによる推測を含む解説("なぜ上振れしたと考えられるか"のような分析文をAIが独自に組み立てる機能)は、**将来拡張とし、MVPでは実装しない。**

MVPで表示する情報:

- 公式発表・公式資料からの抜粋
- 信頼できる情報源への出典URL
- 結果の背景に関する事実ベースの要約(推測を含まない)

**出典が取得できない場合は、説明文自体を生成・表示しない。** 「情報なし」と表示する。

### 12.3 将来拡張: AIによる乖離理由分析

将来的に、AIによる要因分析・市場反応の整理・過去イベントとの比較説明を追加する。その際は以下を必ず満たす構造とする(詳細は概要設計書11章参照)。

- 生成された説明文には、根拠となった出典URL・情報源を明示する
- 事実(公式発表由来)・ニュースによる説明・市場関係者の見解・AIによる要約・AIによる推測、を区別して表示する
- 出典が確保できない場合はAIが推測で説明文を生成しない
- 生成日時・AI生成であることを明示する

AIは価格を予測しない(11.3節と同様、将来もこの方針を維持)。

## 13. 過去イベント分析

### 13.1 表示内容

同一指標の過去イベントを一覧表示する(Date / Forecast / Actual / Surprise / 5m Move等)。

### 13.2 対象件数とデータ品質

「過去◯件」という固定件数に機械的に依存せず、**「分析可能な直近N件」**を基本とする。すなわち、データ品質が揃っている(data_statusが完全な)イベントのみを対象とし、目安件数(20件相当)に届かない場合は実際に確保できた件数で表示する。

**ユーザーには、母数(何件中何件のデータで算出したか)を提示する。** 例: 「過去20回中18回のデータで算出」

---

## 14. 過去イベント統計

同一指標・FX Pair単位で、平均変動・平均絶対変動・最大変動・最小変動・上昇回数・下落回数・変化なし回数を、時間別(1分・5分・15分・30分・60分)に算出する。

**統計計算の対象は、データが揃っている(data_status=complete)イベントに限定する。** 欠損・不完全なイベントを平均・最大・最小の計算に混入させてはならない。除外した件数も含め、母数を13.2節と同様にユーザーへ提示する。

**Database**: PostgreSQLを第一候補とする。

## 27. 推奨データモデル(概要)

Indicator / **IndicatorFxPair**(Indicator↔FXPairの多対多関連) / EconomicEvent(イベントのメタデータ) / **EventSnapshot**(発表時点の値。EconomicEventとは別Entity、DB詳細設計でHQ確定・2026-09) / EventRevision / **EventExplanation**(乖離理由、MVP必須) / FXPair / FXPrice / EventPriceReaction / Person / SpeechEvent / SpeechPriceReaction

**IndicatorFxPair**は、「関連通貨ペア表示」に必要な、指標ごとの分析対象FXペアを固定文字列ではなく関連テーブルとして管理するために新設した(HQ回答、2026-09)。具体的なカラム・制約はDB詳細設計で確定する。

詳細なER設計は概要設計書5章・詳細設計で定義する。

## 28. データ処理

```
経済指標API
  ↓
Economic Event(Snapshot)取得
  ↓
Database保存(不変)
  ↓
Surprise計算(Forecastがnullの場合はSurpriseもnull)
  ↓
FX価格取得(9章の時刻同期ルールに従う)
  ↓
1/5/15/30/60分後の価格取得
  ↓
pips計算
  ↓
EventPriceReaction保存
  ↓
アプリ表示
```

後日の改定情報が判明した場合は、別途EventRevisionとして追記するのみで、上記の計算結果は再計算しない(5.1節)。

## 29. 時刻処理

9章の内容を要件として再掲する。UTCをDB基準時刻とし、ユーザー表示時にローカルタイムへ変換する。DST(夏時間)・APIごとのtimestamp仕様差異を考慮し、正規化した上で保存する。

## 30. データ品質

**Critical**として扱うデータ: 発表日時・Forecast・Actual・Previous・FX価格timestamp・FX価格。

これらのデータ欠損・異常値を検出し、`data_status`として保持する。**価格データ・イベントデータが不完全な場合、推測値を生成してはならない。** 欠損時は`N/A`として扱う。

統計・過去比較は、データが揃っているイベントのみを対象とする(13章・14章)。

## 37. 最重要プロダクト要件

本アプリの価値の中心は、

```
経済イベント → 市場予想 → 実際の結果(発表時点の値) → 予想との差
  → なぜ差が発生した?(出典付き事実) → 為替はどう反応した?
  → 過去も同じだった?(データ品質の揃った件数で)
```

をユーザーが短時間で理解できることである。単なる「経済指標カレンダー」や「FXチャートアプリ」にはしない。過去に発表された値が後日改定されても、当時の市場反応の分析結果は書き換わらない、という一貫性を製品の信頼性の核とする。
