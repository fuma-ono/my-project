# kashikari(貸し借り)Growth戦略 — GROWTH-HQ方針記録(2026-09-11)

オーナーより「kashikariのGrowthに対する期待値・今後の方針」について指示を受けた。以下、方針として記録する。**GROWTH-HQ**は、この方針に基づいてkashikariのユーザー獲得〜収益化サイクルを自律的に検証・改善する機能(マーケティング部・グロース/運用部・データ分析部の合同ミッション、`docs/ORG.md`の部署体制上で運用)を指す。kashikari本体(アプリ)の開発は開発部(別ブランチで進行中、`.github/workflows/kashikari-ios-manual-build.yml`参照)が担当し、GROWTH-HQはユーザー獲得・活性化・継続・収益の検証と改善提案に責任を持つ。

## 1. kashikariのGrowth上の位置づけ

kashikariは、GROWTH-HQにとって最初の本格的なGrowth検証対象である。目的はSNSフォロワー数を増やすことそのものではない。最終目的は、次の成長ループを実際に成立させることである。

```
認知 → インストール → 初回利用(Activation) → 招待(Invitation) → 継続(Retention) → 収益(Revenue)
```

このループのどこかで詰まっている限り、投稿数を増やしても事業としては前進しない。GROWTH-HQは常にこのループ全体を見て、どこがボトルネックかを判断する。

## 2. 現時点の期待値

kashikariが短期間で大規模アプリになることは前提にしない。まず検証すべき問いは、

> 「貸し借り・立替・精算という問題に対して、ユーザー獲得施策が機能するか」

である。初期段階で重視する指標は次の通りで、**単純な再生数・フォロワー数は最終KPIとして扱わない**(あくまで先行指標の一つ)。

- コンテンツの反応(再生・保存・シェア・コメント)
- Store遷移率
- Install数
- Activation率(初回の貸し借り登録)
- 招待数・招待経由の新規Install
- Retention(継続利用)
- オーガニック流入比率

## 3. 狙うユーザー課題(コンテンツの入口)

Growthでは「kashikariというアプリ」を直接売るのではなく、「お金に関する面倒な問題」を入口にする。優先的に検証するシーンは以下の通り。

| シーン | 刺さる痛み |
|---|---|
| 旅行 | 旅行後、誰が誰にいくら払うか分からない |
| 飲み会 | 立替した人が損をする |
| 友人間 | 少額を何回も貸している |
| カップル | 細かい立替を覚えていない |
| グループ | 誰が払って誰が払っていないか分からない |
| サークル | 複数人の会計管理が面倒 |

コンテンツ企画・Hook検証は、このシーン×痛みの組み合わせ単位で行い、どの組み合わせが最も反応するかをデータで確認する。

## 4. 最も重要なGrowth仮説: Invitation Loop

kashikariの成長性は「1人を獲得すること」ではなく、「1人が複数人を連れてくる」構造を作れるかどうかにかかっている。重点的に検証するループは以下。

```
Install → 貸し借り登録 → 相手を招待 → 相手もkashikariを利用
  → 別の貸し借りが発生 → さらに招待
```

このInvitation Loopが機能するかどうかを、他の指標より優先して検証する。Invitation Loopが成立しないまま広告投資を拡大するのは避ける。

## 5. 初期投資の考え方

最初から大規模な広告投資は前提にしない。まずオーガニック施策で以下を検証する。

- どの問題(シーン)が刺さるか
- どのHookが強いか
- どのSNSが強いか
- どのユーザー層が強いか
- どのCTAが強いか

勝ちパターンが確認できてから、広告・インフルエンサー起用・投稿量の拡大など、投資を伴う施策の検討に進む。

## 6. 自律思考の基準: ボトルネック診断

GROWTH-HQは「毎日SNSに投稿するだけの運用」ではない。毎回の意思決定で「現在の最大Growthボトルネックはどこか」を判断し、症状に応じて打ち手を変える。

| 症状 | 診断 | 打ち手 |
|---|---|---|
| 再生数が少ない | Content→Reachが弱い | Hook・テーマ・動画構成を改善 |
| 再生数は多いがInstallが少ない | Reach→Installが弱い | CTA・プロフィール・Store導線を改善 |
| Installは多いがActivationが低い | Install→Activationが弱い | 開発部(APP-FACTORY相当)へオンボーディングUX改善を提案 |
| Activationは高いがRetentionが低い | 継続理由が弱い | 継続利用理由を分析(通知・リマインド・未精算の可視化等) |
| Retentionは高いが収益が低い | マネタイズが弱い | Premium・広告・価格・課金導線を分析 |

指標が伸びない場合に「様子見」を続けることは禁止する(`docs/ORG.md`の意思決定原則「数字が伸びない場合: 黙って様子見しない」と同一方針)。

## 7. 長期的な拡張仮説

kashikariが成功した場合、「貸し借りアプリ」という単一カテゴリに閉じず、以下のような利用シーンへ拡張できる可能性がある。

精算 → グループ会計 → 旅行 → サークル → カップル → 日常のお金管理

ただしこれは仮説であり、実データで需要を確認してから拡張の是非を判断する。先回りしてスコープを広げない。

## 8. 収益化の方針

収益源の候補は Premium / 広告 / 将来的な追加課金 / その他マネタイズ。ただし短期の売上を優先してUXを壊すことは禁止する。判断基準は次のバランス。

```
Revenue × Retention × User Value
```

収益施策の導入前に、Retentionを損なわないかを確認する。

## 9. 撤退・方向転換の基準

「投稿を続ければいつか伸びる」という考え方は採用しない。一定量のデータを取得した上で、次の状態が継続する場合は改善可能性を分析する。

- 特定ユーザー層に刺さらない
- Content→Installが弱い
- Install→Activationが弱い
- Retentionが弱い
- Invitation Loopが成立しない
- LTVが低い

改善可能性が低いと判断した場合、以下をHQ(社長)に提案する。

- ターゲット変更
- ポジショニング変更
- 利用シーン変更
- 収益モデル変更
- 投資縮小
- 撤退

## 10. 成功時の対応

高いRetention・強いInvitation・オーガニック成長・安定したInstall・課金・広告収益・良好なLTVが確認された場合、GROWTH-HQはkashikariへの投資拡大を提案する。その際は「なぜ伸びたのか」を分析し、成功パターンを会社のGrowthシステムとして標準化する(次の事業に転用できる形でドキュメント化する)。

## 11. 会社全体への期待値

kashikariの価値はkashikari単体の売上に限らない。ここで得られる以下の知見を、次のアプリ・事業に転用する。

- ユーザー獲得方法
- SNSコンテンツの型
- ASO
- Activation設計
- Retention設計
- Referral(招待)設計
- Monetization設計
- 広告運用
- Growth分析手法

```
kashikari → Growth知見 → App B → Growth知見 → App C
```

という会社全体の学習サイクルを作ることが狙いである。

## 12. まとめ: GROWTH-HQに期待する役割

GROWTH-HQの役割は「kashikariをSNSで宣伝すること」ではなく、「kashikariが市場で成長できる条件を自ら発見し、仮説を立て、実験し、結果を分析し、改善を繰り返すこと」である。得られたGrowth知見は会社全体の資産として次のアプリへ引き継ぐ。最終目標は、**どんなアプリを作ってもユーザーを獲得して成長させられるAI Growth Machine**を作ることである。
