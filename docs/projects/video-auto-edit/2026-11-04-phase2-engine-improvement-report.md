## 2. P12: 書き出しのメモリ

### 2.1 原因
現行方式(legacy)は、同じ入力映像を区間の数だけ trim で分岐し、最後に concat でつなぐ。concat が前の区間を処理している間、後の区間で使う**未圧縮のフレームがメモリに溜まり続ける**。そのため、メモリは「出力に残す映像の長さ × 解像度」に比例して増える。

### 2.2 比べた方式
| 方式 | 内容 |
|---|---|
| legacy | 現行方式 |
| select | 1本の映像ストリームに `select` で残すフレーム番号を指定し、`setpts` で時刻を詰める(単一ストリーム) |
| segments | 区間ごとに別プロセスで中間ファイル(無劣化)へ書き出し、連結してから仕上げる(2回エンコード) |

3方式とも共通で、次の2つを行う。
- 残す区間の境界を**映像のフレーム境界にそろえる**(最大で半フレーム=約17ms動く)
- 音声は同じ境界で**サンプル単位**に切る

こうすると、区間ごとに映像と音声の長さが一致し、区間が増えてもずれが積み重ならない。

## 3. P11: BGM と声の音量

### 3.1 方式
| 方式 | 内容 |
|---|---|
| legacy(修正前) | BGM を元の0.35倍に固定し、サイドチェインで下げ、最後に全体を loudnorm(動的)でそろえる |
| duck_sc | 声を -16 LUFS に**静的に**そろえる(ゲイン → 軽い圧縮 → 測り直して補正)。BGM も声から12 LU 下に静的にそろえ、サイドチェイン圧縮(attack 80ms、release 700ms)で下げる。最後にピークリミッター |
| **duck_vad** | 声と BGM は duck_sc と同じ。BGM の下げ幅は、**発話区間(VAD)から作った滑らかな音量カーブ**で決める。発話中は -6 dB。下げ始めは発話の0.25秒前から、戻しは0.6秒かける。声の大小に左右されない |

### 3.2 実動画での計測(medium + VAD、同じカットで方式だけ変更)
「声 − BGM」は、400ms の窓ごとに、声と BGM を個別に測った momentary ラウドネスの差。発話中の窓だけを集計した。

| 動画 | 方式 | 声 − BGM 中央値 | 下位5% | 最小 | BGM が声より大きい窓 | 下げ幅の揺れ(標準偏差) | 100msで3dB超の変化 | 出力のラウドネス |
|---|---|---|---|---|---|---|---|---|
| 動画1 | legacy | **-10.3 LU** | -20.9 | -29.8 | **210 / 252** | 1.21 dB | 0回 | -13.6 LUFS |
| 動画1 | duck_sc | 27.1 LU | 17.9 | 6.9 | 0 / 252 | 2.04 dB | 5回 | -16.1 LUFS |
| 動画1 | **duck_vad** | **19.5 LU** | 12.9 | 4.1 | **0 / 252** | 0.23 dB | 1回 | -16.0 LUFS |
| 動画2 | legacy | **-7.9 LU** | -21.3 | -33.1 | **161 / 220** | 1.77 dB | 2回 | -13.7 LUFS |
| 動画2 | duck_sc | 26.8 LU | 13.5 | -1.2 | 1 / 220 | 2.38 dB | 5回 | -16.0 LUFS |
| 動画2 | **duck_vad** | **18.5 LU** | 10.4 | -2.0 | **1 / 220** | 0.24 dB | 1回 | -16.0 LUFS |
| 動画3 | legacy | 6.2 LU | -3.2 | -6.9 | 50 / 260 | 2.22 dB | 1回 | -14.8 LUFS |
| 動画3 | duck_sc | 27.3 LU | 21.5 | 19.4 | 0 / 260 | 0.82 dB | 0回 | -16.0 LUFS |
| 動画3 | **duck_vad** | **18.8 LU** | 14.0 | 12.5 | **0 / 260** | 0.00 dB | 0回 | -16.0 LUFS |

- duck_vad の最終実行値(テロップ修正後の再実行)を記載した。duck_sc と legacy は、その直前の実行値(カットは同じ)
- 動画2で BGM が声を上回った1窓(400ms)は、出力の 20.8秒付近。3方式とも最悪値がこの時刻で、声が非常に小さくなる瞬間と考えられる。**オーナーの試聴で要確認**
- 声の音量は、小さい動画ほど大きく持ち上げた: 動画1 +16.3 dB、動画2 +13.8 dB、動画3 +7.0 dB(さらに圧縮後の補正 +3.7〜4.7 dB)。雑音も同じだけ大きくなる点は未評価(§7)
- 無音時の戻り: 実動画は無音がカットされるため測れない。そこで、カットしない設定の合成音声(無音を含む窓128個)で測った。3方式とも、無音中の BGM は下げ幅0 dB(元の音量)に戻った。発話中の下げ幅は、duck_vad -6.0 dB(揺れ 0.05 dB)、duck_sc -15.1 dB(0.62 dB)、legacy -8.2 dB(1.52 dB)

**推奨: duck_vad**。声との差が3本でほぼ一定(18.5〜19.5 LU)で、下げ幅の揺れ(ポンピングの目安)が最も小さい。計算は numpy の配列演算だけで、追加費用はない。duck_sc は BGM がほとんど聞こえないほど下がり(声との差 約27 LU)、揺れも大きかった。

既定の音量設定(声 -16 LUFS、BGM は声より 12 LU 下、発話中さらに -6 dB)は、計測をもとにした開発者の仮の値。BGM が聞こえすぎるか、聞こえなさすぎるかは、オーナーの試聴で決める必要がある。

## 4. テロップ(P8〜P10)

### 4.1 変更内容
- 文の区切り: 「。」「？」「！」に加え、半角の「?」「!」でも必ず区切る。1つの語の途中に文末記号があるときは、文字数の比で時刻を配分して分ける
- 改行・分割: BudouX の文節境界を候補にする。ただし、**数字(+単位)・年月日・時刻・英単語の内側**では区切らない(例「2026年11月1日」「14時28分」「1.5倍」「iPhone」)。読点の直後を優先するが、上下の行の長さが大きく偏る場合は均等な位置を選ぶ
- 1回の表示は最大2行。入りきらない文は、表示回数が最少で、なるべく均等になるように複数回に分ける(動的計画法)
- はみ出し防止: IPAゴシックの実寸(Pillow で計測、太字と縁取りの余裕込み)で、1行の幅が「画面幅 − 左右余白」に収まるかを判定する。libass の自動改行は止めた
- 表示時間: 0.8秒未満の表示は、同じ文の隣とまとめるか、前後の空き時間に延ばす。それでも短いときは、隣の表示と2行で並べる。0.3秒未満の空白は、ちらつかないよう次の表示まで延ばす。表示が重ならないようにする

## 5. 言い淀み(P13)

### 5.1 変更内容
- 表記ゆれの正規化: カタカナ→ひらがな、小書き文字→通常の文字。長音記号・波線・促音と、直前と同じ母音の伸ばしは除く(「まぁ」「まー」「まあ」→ 同じ語)
- 語の種類ごとの条件(文字列の一致だけでは削除しない)
  - 常に言い淀みになりやすい語(えー、えーと、あー、うーん、まあ など): 後ろに句読点・0.1秒以上の間・伸ばし・別の言い淀みがあるとき削除
  - 1文字の語(え・あ・う・ま・ん): 単語の一部のことがあるので、句読点・間・伸ばしがあるときだけ削除(「次も言い淀み」は理由に使わない)
  - 文脈で意味が変わる語(あの、その、なんか、うん): 後ろに句読点がある / 0.25秒以上の間がある / 0.35秒以上伸ばしている / 次も言い淀み、のどれかのときだけ削除。満たさなければ指示語として残す
- すべての候補について、判定と理由を評価シートに記録する

- 開発中に見つけた誤検出: 改善の途中版では、「うまく」が「う」「ま」「く」の1文字ずつに分かれて認識された箇所で、「う」を「次も言い淀み」という理由で削除しようとしていた。1文字の語の条件を分けて防いだ。修正後、3本で必要な発話を言い淀みとして削除した例は、自動チェック(誤カット候補・高)で0件

- **未評価:** Whisper が文字にしなかった言い淀みが残っていないか。言い直し(「〜じゃなくて〜」)の除去は、今回も対象外

| 声を大きく持ち上げたことによる雑音の増加(動画1は +16 dB 以上) | **未評価**。雑音除去は今回の範囲外 |
| 仕上がりの音量 -16 LUFS(多くの動画サイトの目安 -14 LUFS より小さい) | 設定で変更できる(`VEDIT_VOICE_LUFS`)。どちらにするかは HQ の判断事項 |
| 可変フレームレート(VFR)の素材 | 書き出しで `fps` フィルタにより固定フレームレートに変換する作り。実際の VFR 素材では**未検証** |
| 3分・5分の**実動画** | 合成素材でのみ検証。実動画の長尺は未検証(Whisper の処理時間は約0.5倍速で長さに比例する見込み。未計測) |
| 文字起こしの誤り(年号、「関係線」など) | 今回の範囲外。改善していない |
| 失敗率 | 改修直後の最初の実行では、3本ともスクリプトの不具合(numpy の値を JSON に書けない)で失敗した。修正後の実行(主評価3本 × 2回、ミックス比較6本、合成音声3本)と、ベンチマークで完了させる対象の10件では、失敗は0件だった。legacy の長尺2件は、意図的に停止したもの。母数が小さく、失敗率としての信頼性は低い |
| small モデルの再評価 | 今回は実施していない(主評価は medium) |
| テロップの表示がちらつかないか、行替えが読みやすいか | 自動チェックと画面キャプチャのみ。動画を通しで見た確認は未実施 |

## 8. HQ に判断してほしいこと

1. **カット方式の既定値を vad に変えるか**(今回の主評価で問題は見つかっていない。volume は背景音のある動画でカットされない)
2. **書き出しを select 方式に確定してよいか**(他の方式より速く、メモリが一定)
3. **ミックスを duck_vad に確定してよいか**。あわせて、オーナーの試聴をもとに音量の目標値を決める: 仕上がり -16 / -14 LUFS、BGM の大きさ(声との差 約19 LU)
4. **言い淀みの判定のしきい値**(伸ばし 0.35秒、間 0.25秒)をこのままでよいか。動画2の最後の「あの」の試聴結果で決めたい
5. 次の工程として、次のどれを優先するか
   - (a) 実動画の長尺(3〜5分)での通し検証
   - (b) 声の雑音除去
   - (c) 文字起こしの誤りへの対策(固有の語の登録、人が直す画面など)
   - (d) 編集計画 JSON を中心にした本実装の設計
6. 本実装(iOS を含む)の開始は、引き続き HQ の承認待ちとする
