- 作成日: 2026-10-31

- 範囲: 環境確認、無料技術の調査、最小構成の使い捨て検証(PoC)。**アプリ本体の実装は行っていない。有料サービスの契約・利用はしていない。**

## 0. 結論(先に要点)

1. **無料のローカル技術だけで「文字起こし → 無音・言い淀みカット → 同期テロップ → BGM → 書き出し」が一通り動いた。** 34.8秒のテスト動画を約25秒(4コアCPU、GPUなし)で 16.8秒の編集済みMP4にした。
2. ただし入力は**合成音声(TTS)**であり、**実際の人の声・雑音・BGM入り素材では未検証**。ここが次の最重要検証項目。
3. 「映像の意味理解」「見どころ判定」「プロ並みの構成判断」は**無料の範囲では限定的**。ルールベース+小型ローカルモデルで段階的に作るのが現実的。
4. iOSアプリ化では、**編集ルール(何を切る・テロップをどう分ける)は流用可能**だが、**FFmpeg/Python部分は作り直し**(AVFoundation と Apple の端末内音声認識)になる見込み。

## 2. 検証結果(テスト済み・合成音声)

### 2.1 テスト入力
- `poc/make_sample.py` で作成。pyopenjtalk(無料・オフラインの日本語音声合成)で 7 文を読み上げ、間に 1.0〜3.0 秒の無音と「えーと」「あのー」を挿入。映像は FFmpeg のテストパターン。
- 長さ 34.8 秒、1280x720、30fps。
- 実際の人の声を使わなかった理由: 権利上問題なく取得できる日本語の実音声サンプルを、この環境から入手できなかった(Wikimedia はレート制限)。

### 2.2 パイプライン(`poc/poc_pipeline.py`)

| 工程 | 使った技術(すべて無料) | 結果 |
|---|---|---|
| 1. 音声抽出 | FFmpeg | 0.2秒 |
| 2. 文字起こし | faster-whisper(small, CPU, int8)+ 単語タイムスタンプ | 6.6〜8.2秒。7文すべて認識。誤り1か所(「部分**を**」→「部分**の**」) |
| 3. 無音検出 | FFmpeg `silencedetect`(-35dB, 0.5秒以上) | 0.1秒。12区間検出 |
| 4. 不要部分カット | 無音区間+言い淀み語を除外し、前後0.12秒の余白 | 34.8秒 → 16.8秒。「えーと」「あのー」も除去 |
| 5. テロップ | 単語タイムスタンプ→行分け→ASS字幕、BudouX で改行位置決定、FFmpeg `ass` で焼き込み | 7行。2段表示・日本語描画を画像で目視確認(`poc/frame_sample.png`) |
| 6. BGM | 既存 `bgm-pipeline`(study_lofi_chill)を読み取り専用で呼出、`sidechaincompress` で声の間だけ音量を下げる(ダッキング)、`loudnorm` | 生成5〜8秒。統合ラウドネス -14.8 LUFS(目標-14) |
| 7. 書き出し | libx264 veryfast CRF20 + AAC 192k | 5.5〜10秒。H.264 1280x720 / AAC 48kHz |

合計: 約25〜27秒(モデル読み込み込み)。

### 2.3 Whisper モデル別の実測(同じ 34.9 秒の音声、CPU int8)

| モデル | 文字起こし時間 | 実時間比 | 最大メモリ | 認識結果の質 |
|---|---|---|---|---|
| base | 2.7秒 | 0.08 | 約0.5GB | 「BGM」→「VGM」、「付けて」→「続けて」など誤り多め |
| **small** | 6.8秒 | 0.20 | 約0.8GB | 誤り1か所。句読点が整っていて行分けしやすい |
| medium | 17.2秒 | 0.49 | 約2.8GB | 誤りなし |
| large-v3-turbo | 14.9秒 | 0.43 | 約2.6GB | 誤りなし。ただし「あのー」を「あのお!」と出力し、言い淀み辞書に一致しなかった |

モデル容量は合計 3.6GB をダウンロード(初回のみ、無料)。

### 2.4 検証中に見つかった問題と対処(PoC内で対処済み)

| 問題 | 原因 | PoCでの対処 | 本実装で必要なこと |
|---|---|---|---|
| faster-whisper が起動時に失敗 | PyAV 19 と faster-whisper 1.2.1 の非互換 | 音声を自前で読み込んで配列で渡す | **依存バージョンの固定**(lockファイル) |
| 「えーと」が「えー」+「と。」に分割され「と」が残った | Whisper のトークンは単語単位ではない | 連続トークンを結合して照合 | 言い淀み検出の評価データを作り、精度を測る |
| テロップ「まず」が消えた | 単語の時刻が実際の発話とずれ、削除区間に落ちた | 最寄りの残存区間に寄せる | 必要なら強制アライメント(下記)を検討 |
| 「BG/M」と単語途中で改行 | 同上 | BudouX(Google製、Apache-2.0)で文節境界改行 | そのまま採用可 |
| **既存 `bgm-pipeline` が一部の長さでエラー** | `core.widen` でサンプル数が1ずれる(例 `--minutes 0.2945`) | 30秒単位に切り上げて生成し切り詰め | **既存ファイルは変更していない。HQ判断で別途修正可否を決めてほしい** |

## 3. 推奨技術構成(検証段階)

```
入力動画
 ├─ FFmpeg: 音声抽出(16kHz mono)
 ├─ faster-whisper (small、精度不足時 medium / large-v3-turbo): 文字起こし+単語時刻
 ├─ FFmpeg silencedetect (+ 将来 Silero VAD): 無音区間
 ├─ 編集判断(Python、ルールベース): 残す区間・言い淀み除去・テロップ行分け(BudouX)
 │     → 中間データ「編集計画(JSON)」として保存  ★ここが将来のiOS版でも流用する中核
 ├─ BGM: bgm-pipeline の自前生成曲(または権利確認済み曲)+ ダッキング + loudnorm
 └─ FFmpeg: カット・ASS字幕焼き込み・音声合成・H.264書き出し(1回のエンコード)
```

設計上の要点: **「解析」と「編集計画(JSON)」と「書き出し」を分ける。** 編集計画は「どの区間を残すか、どのテロップをいつ出すか、BGMの音量」だけを持つ純粋なデータにする。これで書き出し部分を FFmpeg から iOS の AVFoundation に差し替えても、判断ロジックと評価データはそのまま使える。

## 4. 無料で実現できる機能 / 無料では難しい機能

### 4.1 無料で実現できる(PoCで確認済み、または確度が高い)

| 機能 | 技術 | 状態 |
|---|---|---|
| 日本語文字起こし | faster-whisper(MIT)/ Whisper モデル(MIT) | テスト済み(合成音声) |
| 無音カット | FFmpeg silencedetect | テスト済み |

| 発言同期テロップ | ASS + libass + BudouX | テスト済み |
| BGM付与・ダッキング・音量正規化 | 自前生成BGM + FFmpeg | テスト済み |
| 書き出し(横・縦) | FFmpeg / libx264 | 横のみテスト済み。縦(9:16)は未検証 |

### 4.2 無料では難しい・品質が限定的

| 機能 | 理由 | 無料での代替 | 有料にした場合 |
|---|---|---|---|
| 映像の意味理解・見どころ判定 | 高性能な視覚言語モデルは GPU なしでは非常に遅い | 字幕テキスト+動き量+顔検出によるルール採点。小型の画像特徴モデル(CLIP/SigLIP系、無料)で類似場面をまとめる程度 | 外部のマルチモーダルAPI。1本数円〜数十円程度と想定されるが**未見積もり・未契約** |
| 構成の組み替え(要約、冒頭フック作成) | 文章理解が必要 | ローカルLLM(llama.cpp 等)。CPUでは遅く品質も不安定 | 外部LLM API(上と同様に未見積もり) |
| 強調テロップ・効果音・ズーム等の「プロらしい演出」の自動判断 | 正解の定義が難しく、学習データが必要 | テンプレート+ルール(例: 疑問文で効果音、数値を含む行を強調) | 有料でも決定的な解はない |
| 雑音・音楽が入った素材での高精度な文字起こし | 小型モデルは誤りが増える | medium / large-v3-turbo(遅くなる)、音声分離(Demucs、無料だが重い) | — |
| 多人数の話者分離 | pyannote は無料だがモデル利用に HF 登録・規約同意が必要 | 単一話者に限定して始める | — |
| サーバーで多数の利用者の動画を処理 | CPU 時間・保存領域・通信量が必ず発生する | 端末内処理(iOS)またはユーザーPCでの処理に寄せる | クラウドのサーバー費(要見積もり) |

## 5. BGM の利用許諾と商用利用時の注意(調査のみ・法的助言ではない)

1. **最も安全なのは自前生成(既存 `bgm-pipeline`)。** 権利は自社に帰属し、Content ID の誤検出も起きにくい。今回の PoC もこれを使った。ただし音楽の質・種類は限られる。
2. **フリーBGMサイトの曲を「アプリに同梱して利用者に使わせる」のは、多くのサイトで「素材の再配布」に当たり禁止または要確認。** 動画制作者が自分の動画に使うのとは扱いが違う。例: DOVA-SYNDROME は動画での商用利用は可能とされる一方、音楽が主体のコンテンツでの利用は禁止と案内されており、アプリ組み込みの可否は公式の「音楽利用ライセンス」「利用規約」で個別確認が必要(未確認)。
3. **YouTube オーディオライブラリの曲は、YouTube 用動画での利用を前提とした規約**であり、他アプリへの組み込み・配布用途には使えないと考えるべき(要規約確認)。
4. CC0/CC BY 曲でも、**Content ID に第三者が登録している例**があり、投稿後に収益化停止や申し立てを受けるリスクがある。
5. JASRAC 等の管理楽曲(市販曲)は、利用者が自分で許諾を取らない限り使わせない設計にする。
6. AI生成音楽サービスの曲は、サービスの規約(商用利用・再配布の可否、有料プラン限定かどうか)で扱いが変わる。現時点で新規契約は提案しない。

**推奨:** 当面は自前生成BGMのみ。外部曲を採用する場合は、曲ごとに「出典・規約URL・確認日・クレジット要否・アプリ同梱可否」を記録する台帳を作り、HQ承認後に追加する。

## 8. iOS アプリ等から利用する場合

| 部分 | 流用 | 理由 |
|---|---|---|
| 編集ルール(残す区間・言い淀み・テロップ行分け・表示時間) | **流用可**(Swiftへ移植、または同じJSON仕様で実装) | 純粋なロジック |
| 編集計画 JSON の形式 | **流用可** | 端末側・サーバー側の共通仕様にする |
| 評価用の動画・正解データ | **流用可** | 品質比較の基準になる |
| BGM 曲(自前生成した音声ファイル) | **流用可** | 同梱前に権利確認(自前なら問題なし) |
| FFmpeg による書き出し | **作り直し** | iOS では AVFoundation / VideoToolbox が標準。FFmpeg を iOS に組み込む定番だった FFmpegKit は 2025年に開発終了・配布終了と告知されている。さらに今回の FFmpeg は GPL ビルド(libx264)で、App Store 配布とは相性が悪い |
| faster-whisper(Python) | **作り直し** | iOS では Python が使えない。代替は Apple の端末内音声認識(iOS 26 の SpeechAnalyzer/SpeechTranscriber、日本語対応と報告あり、**未検証**)または whisper.cpp(MIT、iOS 対応) |
| ASS 字幕焼き込み | **作り直し** | Core Animation のテキストレイヤーで描画 |
| BudouX | 一部流用可 | JavaScript 版があり、ルールの考え方は同じ |

別案: iOS アプリは撮影・アップロードだけにし、処理はサーバー(今回のPython構成)で行う。この場合はコードを流用できるが、**サーバー費用が毎月かかる**。費用最小の方針なら、**端末内処理を基本**にするのが望ましい。

## 9. 想定される技術的リスク

1. **実素材での精度低下**(雑音、複数話者、早口、方言、BGM入り素材)。今回の合成音声は理想的すぎる。
2. **単語時刻のずれ**によるカット位置・テロップ位置のずれ。語頭が切れる「ブツ切れ」が起こりうる。
3. **言い淀み辞書の取りこぼし・誤検出**(モデルによって「あのー」「あのお!」等と表記が揺れる。「あの人」の「あの」を誤って削る危険)。
4. **依存ライブラリの非互換**(今回 PyAV で実際に発生)。
5. **処理時間**: 長尺動画や medium 以上のモデルでは CPU のみだと遅い。
6. **「プロらしさ」の評価基準が曖昧**で、改善の判定ができない。
7. **ライセンス**: FFmpeg の GPL 構成、BGM の再配布、フォントの同梱条件(IPAフォントは同梱可能だが条件あり、要確認)。
8. **既存 `bgm-pipeline` の不具合**(長さにより失敗)。
9. 本環境は一時的で、**常設の開発・処理環境がまだない**。

## 10. 最初に検証すべき項目(優先順)

1. **実際の人の声の動画での精度確認**(最重要)。オーナーが撮影した 30秒〜1分の動画を 3〜5本(1人で話す、屋内、雑音あり、BGMあり等)。
2. その動画で small / medium / large-v3-turbo の誤り数とカット位置の自然さを比較し、採用モデルを決める。
3. 無音のしきい値(-35dB / 0.5秒)と余白(0.12秒)の調整。語頭・語尾が切れないか耳で確認。
4. 縦動画(9:16)の書き出しとテロップ位置。
5. iOS 端末内での文字起こし(Apple SpeechTranscriber)の精度・速度の比較(Mac+実機が必要。費用0円で可能か、開発者アカウントの要否を含めて確認)。

  - 出力動画をオーナーが視聴し、「そのまま使える/手直しが必要/使えない」を判定

### 次の作業B: 編集計画 JSON の仕様化と最小エンジン化(Aの結果を見てから)
- 解析・編集計画・書き出しの3層に分けた最小のコマンドラインツールを作る(リポジトリ内に新規ディレクトリ。既存プロジェクトは変更しない)
- 完了条件: 同じ入力から同じ編集計画 JSON が出ること、単体テストがあること、依存バージョンが固定されていること

### HQ に判断してほしいこと
1. 実素材(テスト動画)の提供方法と、動画に映る人物の同意の扱い
2. 処理の基本方針: **端末内処理(費用最小)** か サーバー処理(開発は速いが運用費あり)か
3. 既存 `bgm-pipeline` の長さ不具合を修正してよいか(別作業として)
4. 当面のBGMを自前生成のみに限定してよいか
