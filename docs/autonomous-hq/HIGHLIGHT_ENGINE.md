# AI 編集エンジン(複数動画 → 最高の1本)の構成と品質検証 PoC

最終更新: 2026-11-21(UTC)。オーナーの「コンセプト・開発方針」(2026-11-21)の最優先項目
「複数の動画を理解し、AI が最高の1本を自動編集する」に対する技術構成と、品質検証の進め方。

## 1. 方針
- 完成動画の品質を最優先にする(機能数・速さより優先)。技術的に動くだけでは合格にしない。
- 1つの AI に全部をさせない。次の3層を組み合わせる。
  - **映像を理解する層**: ローカルのモデル
  - **構成を判断する層**: 規則、または LLM
  - **書き出す層**: FFmpeg
- 既存のエンジン(文字起こし・VAD・字幕・音量処理・検証)は作り直さずに使う。

## 2. 構成
| 層 | 役割 | 今の PoC(無料・ローカル) | 品質を上げる選択肢(承認が必要なもの) |
|---|---|---|---|
| 取り込み | 撮影日時・向き・長さ | ffprobe(撮影日時が無ければ更新日時) | — |
| 映像の理解 | 場面の種類・見どころ・画質・顔・動き | CLIP ViT-B/32(ONNX、ゼロショットで10種類の場面と「印象的か」を判定)、YuNet(顔)、OpenCV(鮮明さ・明るさ・動き) | Claude などの画像理解(場面の説明文、表情、出来事の把握) |
| 音の理解 | 会話・盛り上がり | Silero VAD、faster-whisper、音量の山 | — |
| ショット分割 | 場面の切れ目 | CLIP の埋め込みの変化と画の変化 | — |
| 構成の判断 | 選ぶ・重複を整理・順番・長さ・掴み・締め | 規則(planner.py)。次の要素で決める: 全体で標準化した採点、重複の整理、各動画から最低1区間、MMR で多様性、撮影順、冒頭の掴み、最後は景色、素材量から長さ | LLM が区間の一覧と説明から EDL を作る(物語の構成、指示による再編集) |
| 音楽 | BGM と拍 | PoC 用の自動生成(拍の位置が分かる) | 利用許諾のある音源ライブラリ、またはオーナーが用意する音源 |
| 書き出し | つなぐ・合わせる | 拍の倍数の長さでカット、向きの違う素材はぼかした背景で埋める、軽い色調整、会話の間は BGM を下げる、会話の字幕、最初と最後のフェード | 場面に合わせたつなぎ方・演出 |
| 評価 | 品質の確認 | EDL(採用・不採用の理由)、評価シート、コンタクトシート | 実動画での人の評価(オーナー) |

コードの場所:
- `personal-side-projects/video-auto-edit/vae/highlight/`(analyze / planner / music / render / models)

## 4. 品質検証の進め方(実動画が必要)
1. オーナーが撮った実際の動画を 20本前後用意する。旅行などの1日分で、人物・食事・景色・移動が混ざったものが望ましい。
2. 無料の構成(今の PoC)で1本作り、評価シートに次の6項目を記入する。
   - 内容の理解
   - 良い場面の選択
   - 不要な部分の削除
   - 流れ
   - BGM との同期
   - 驚き・満足
3. 承認された場合だけ、同じ素材で LLM の構成判断と画像理解を加えた版を作り、2の結果と比べる。
4. 比べた結果で、製品の構成と原価を決める。

## 5. 処理時間と原価の目安
- **無料の構成**: 解析は素材1分あたり CPU 約1〜2分(文字起こしを含む)、書き出しは完成動画の長さの数倍。外部費用0円。
- **LLM を加える場合の見積もり**(推定。2026-11 時点の公開価格。1ドル=155円として計算)
  - 入力: 20本 × 代表フレーム 8枚 = 160枚の縮小画像(約3万トークン)と、区間の一覧(約1万トークン)
  - 出力: EDL と説明、思考で 約1.5万トークン

| モデル | 1プロジェクトの初回編集 | 月40本(PRO の上限)での原価 |
|---|---|---|
| Claude Opus 5.5 | 約 0.5ドル(約75円) | 約3,000円。価格 1,980円を上回る |
| Claude Sonnet 5.5 | 約 0.24ドル(約37円) | 約1,500円 |
| Claude Haiku 5.5 | 約 0.012ドル(約2円) | 約80円 |

  - AI 再編集は、画像を送り直さず EDL と指示だけを送れば、初回の 1/3 程度の見込み。
  - 画像のトークン数は「幅 × 高さ ÷ 750」での概算。実測は承認後に行う。

承認の条件と、コードでの担保(`vae/highlight/planner_llm.py`、`tests/test_highlight.py`):
| 条件 | 担保 |
|---|---|

| 無断で繰り返し実行しない | 既定は送らない(dry-run)。送るのは `--llm run` のときだけで、1回の実行につき1リクエスト。SDK の自動再試行は切る。失敗しても自動で再実行しない(失敗した回も最悪の見積もり分を計上し続ける) |

| 同じ実動画で無料版と比較 | `python tools/highlight_poc.py <動画> -o <出力> --llm run` で、同じ解析結果から無料版と Sonnet 版の動画を作り、`compare.md` に違いと人による比較の記入欄を出す |

- 見積もり: 素材20本・画像160枚で、入力 約3万トークン、出力の上限 1.2万トークン → 1回の最悪が約40円。500円の予算で、再実行を含めて十分に収まる。
- Claude API のキーは、環境の設定の「環境変数」にだけ置ける(サービスの仕様)。環境を使う人とセッション内のコマンドが読める点に注意。
- refusal(安全上の拒否)になった場合は、自動で別モデルに切り替えず(予算と条件の外のため)、記録して止める。

## 7. BGM の音源: 利用許諾の調査(2026-11-21、規約の公式ページを確認)

わかったこと:
- 「音楽を動画に使う」ライセンスと、「アプリが音源を持ち、利用者が選んで動画に組み込む」ライセンスは**別物**になりやすい。後者は、アプリの利用を明記したライセンス(アプリ向けのライセンス)でないと、組み込みの時点で規約違反になるおそれがある。
- 現実的な道筋は、次のどちらか。どちらも**提供元に書面で確認**してから採用する。

## 8. CC0 音源の調査(2026-11-21 追加。製品への同梱はしない)
**ライセンスの根拠(CC0 そのもの)**: Creative Commons の公式の説明(deed と FAQ)で確認した。
- 商用利用を含め、許諾なしで複製・改変・配布・演奏できる。表示(クレジット)は法的に不要。
- **対象外**: 他の人が持つ権利(肖像権・パブリシティ権・プライバシー)、特許・商標。人格権は、放棄を認めない国がある。
- **「CC0 を付けた人が本当の権利者である保証はない」**。Creative Commons は、CC0 が付いた作品の権利状態を確認していない。疑いがあれば使わないよう勧められている。
- 完成動画への埋め込み、利用者による保存・SNS 投稿は、CC0 の一般的な意味(商用を含めて自由)の範囲。個別に書かれたページは無い。**音源の置き場(itch.io など)の独自の条件は、各ページを確認した範囲では書かれていない**。

**候補**(いずれも itch.io の各ページの「Asset license: Creative Commons Zero v1.0 Universal」と本文で確認。**音源は未取得・未試聴。音質は未確認**):

## 9. 実動画での最初の動作確認(2026-11-22、1本だけ。品質の証明ではない)
- 素材: オーナーが Dropbox に入れた1本(結婚式の受付、4K 29.97fps、35.5秒、453MB)。置き場 `/root/vae-testdata/owner_v1`(Git の外)。**人物(第三者)が写っている**ので、公開しない。
- 無料版で通した結果: 完成 10.2秒(1920x1080、映像と音声のずれ 0.01秒、True Peak -2.6 dBTP、検証 OK)。処理 92 秒(解析 64 秒・書き出し 25 秒、外部費用 0円、4K の入力でも通った)。
- **実動画で見つかった問題**: 拍に合わせる処理が会話の無い区間を最短 2拍(約1秒)にしており、1.0秒の区間ができた → 最短 2.0 秒に修正(`MIN_CUT_SEC`)。
- 1本だけの素材では、複数動画の選択・順番・重複の整理は検証できない。
- **API への送信について**: Sonnet 版は、候補区間の代表フレーム(人物の顔を含む)を API に送る。第三者が写る映像を外部へ送るので、実行の前にオーナーの確認を取る。

### 9.1 オーナーの指摘(2026-11-22): 「字幕がおかしすぎる」「カットが多すぎる」— 原因と修正
**原因(実測)**
- カット: 元動画に場面の切り替わりが 12.3 秒と 25.1 秒の2か所あり、選んだ最初の区間(11.5〜13.5 秒)がその真ん中をまたいでいた。出力の冒頭 2 秒に約0.8秒+約1.2秒の別の場面が並び、さらに2区間目につながって、10 秒の中に切れ目が3つあった。
- 字幕: 文字起こしに `small` モデルを使っていた(雑音の多い複数人の会話で「筋トレ」「タンプシー」「パック」のように崩れた)。しかも、確信度が 0.02〜0.5 の語まで字幕にし、区間をまたいで長く出し続けていた。`medium` に替えても「吐きそうだね」のように怪しい文が残る(確信度 0.48〜0.87)。

**修正**(`tests/test_highlight.py` に回帰テスト 5件)
1. 元動画の切り替わりを検出し(`analyze.detect_cuts`)、区間が切り替わりをまたがないようにする。拍への合わせ込みでも、元の切り替わりの内側に収める。
2. 最短の区間を 2 秒に。完成動画の区間数は「1区間あたり平均 3 秒以上」になる数まで(各動画の代表は残す)。
3. 字幕は、確信度が高い文(語の平均 0.75 以上、どの語も 0.15 以上)だけ。出力の区間ごとに作り、区間をまたがない。**間違った字幕より、字幕なしを選ぶ。**
4. 文字起こしの既定を `medium` に。LLM への指示にも「カットを多くしない」を追加。

**修正後(同じ動画)**: 8.1 秒の1区間(切れ目 0)。字幕は最後の1文だけ(低い確信度の4文を除外)。処理 166 秒(`medium` の文字起こしを含む)。
**残る課題**: 確信度が高くても、文字起こしが正しいとは限らない(最後の字幕に「これはこれは」の重複)。この製品の既存の字幕(単独の話者向け)にも、同じ確信度の条件を入れるか検討が必要。
