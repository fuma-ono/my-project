# AI 編集エンジン(複数動画 → 最高の1本)の構成と品質検証 PoC

最終更新: 2026-11-21(UTC)。オーナーの「コンセプト・開発方針」(2026-11-21)の最優先項目
「複数の動画を理解し、AI が最高の1本を自動編集する」に対する技術構成と、品質検証の進め方。

## 1. 方針
- 完成動画の品質を最優先にする(機能数・速さより優先)。技術的に動くだけでは合格にしない。
- 1つの AI に全部をさせない。次の3層を組み合わせる。
  - **映像を理解する層**: ローカルのモデル
  - **構成を判断する層**: 規則、または LLM
  - **書き出す層**: FFmpeg
- 既存のエンジン(文字起こし・VAD・字幕・音量処理・検証)は作り直さずに使う。

## 2. 構成
| 層 | 役割 | 今の PoC(無料・ローカル) | 品質を上げる選択肢(承認が必要なもの) |
|---|---|---|---|
| 取り込み | 撮影日時・向き・長さ | ffprobe(撮影日時が無ければ更新日時) | — |
| 映像の理解 | 場面の種類・見どころ・画質・顔・動き | CLIP ViT-B/32(ONNX、ゼロショットで10種類の場面と「印象的か」を判定)、YuNet(顔)、OpenCV(鮮明さ・明るさ・動き) | Claude などの画像理解(場面の説明文、表情、出来事の把握) |
| 音の理解 | 会話・盛り上がり | Silero VAD、faster-whisper、音量の山 | — |
| ショット分割 | 場面の切れ目 | CLIP の埋め込みの変化と画の変化 | — |
| 構成の判断 | 選ぶ・重複を整理・順番・長さ・掴み・締め | 規則(planner.py)。次の要素で決める: 全体で標準化した採点、重複の整理、各動画から最低1区間、MMR で多様性、撮影順、冒頭の掴み、最後は景色、素材量から長さ | LLM が区間の一覧と説明から EDL を作る(物語の構成、指示による再編集) |
| 音楽 | BGM と拍 | PoC 用の自動生成(拍の位置が分かる) | 利用許諾のある音源ライブラリ、またはオーナーが用意する音源 |
| 書き出し | つなぐ・合わせる | 拍の倍数の長さでカット、向きの違う素材はぼかした背景で埋める、軽い色調整、会話の間は BGM を下げる、会話の字幕、最初と最後のフェード | 場面に合わせたつなぎ方・演出 |
| 評価 | 品質の確認 | EDL(採用・不採用の理由)、評価シート、コンタクトシート | 実動画での人の評価(オーナー) |

コードの場所:
- `personal-side-projects/video-auto-edit/vae/highlight/`(analyze / planner / music / render / models)
- `tools/highlight_poc.py`

## 3. これまでに確かめたこと(機能の確認。品質の確認ではない)
- **合成素材 8本**(縦と横が混在、合計68秒)
  - 20.9秒の完成動画になった(目標21.9秒)。
  - 8本すべてから1区間ずつ使った。カットはすべて 92 BPM の4拍(2.61秒)ごと。
  - 横の素材は、ぼかした背景で縦に収まった(画で確認)。
  - 映像と音声の長さは一致し、True Peak は -5.7 dBTP。
  - 処理は全体で 51.8 秒(CPU 129 秒)、外部費用は0円。
- **手元の実動画 3本**
  - 2本は画面が真っ黒(音声だけの記録)で、正しく除外した。
  - 1本は床が映った会話の動画。人物の顔は無いのに、場面の種類は「人物」と判定した(CLIP の分類の限界の例)。
  - ハイライトの品質を確かめるのには向かない素材。
- **規則の単体テスト**: `tests/test_highlight.py` 7件(各動画から採用、撮影順、撮り直しの整理、黒い素材の除外、時間の重複なし、拍への合わせ込みと会話を切らないこと、目標の長さ)

## 4. 品質検証の進め方(実動画が必要)
1. オーナーが撮った実際の動画を 20本前後用意する。旅行などの1日分で、人物・食事・景色・移動が混ざったものが望ましい。
2. 無料の構成(今の PoC)で1本作り、評価シートに次の6項目を記入する。
   - 内容の理解
   - 良い場面の選択
   - 不要な部分の削除
   - 流れ
   - BGM との同期
   - 驚き・満足
3. 承認された場合だけ、同じ素材で LLM の構成判断と画像理解を加えた版を作り、2の結果と比べる。
4. 比べた結果で、製品の構成と原価を決める。

## 5. 処理時間と原価の目安
- **無料の構成**: 解析は素材1分あたり CPU 約1〜2分(文字起こしを含む)、書き出しは完成動画の長さの数倍。外部費用0円。
- **LLM を加える場合の見積もり**(推定。2026-11 時点の公開価格。1ドル=155円として計算)
  - 入力: 20本 × 代表フレーム 8枚 = 160枚の縮小画像(約3万トークン)と、区間の一覧(約1万トークン)
  - 出力: EDL と説明、思考で 約1.5万トークン

| モデル | 1プロジェクトの初回編集 | 月40本(PRO の上限)での原価 |
|---|---|---|
| Claude Opus 5.5 | 約 0.5ドル(約75円) | 約3,000円。価格 1,980円を上回る |
| Claude Sonnet 5.5 | 約 0.24ドル(約37円) | 約1,500円 |
| Claude Haiku 5.5 | 約 0.012ドル(約2円) | 約80円 |

  - AI 再編集は、画像を送り直さず EDL と指示だけを送れば、初回の 1/3 程度の見込み。
  - 画像のトークン数は「幅 × 高さ ÷ 750」での概算。実測は承認後に行う。

## 6. 有料 API(Claude Sonnet 5.5)の限定検証(オーナー承認 2026-11-21)
承認の条件と、コードでの担保(`vae/highlight/planner_llm.py`、`tests/test_highlight.py`):
| 条件 | 担保 |
|---|---|
| 最初は Sonnet 5.5 だけ。Opus の検証・本採用はしない | モデル ID を定数で固定(`claude-sonnet-5-5`)。テストで確認 |
| 合計予算の上限 500 円 | 累計を `~/.cache/vae/llm_ledger.json`(Git の外)に記録。送る前に「累計 + この実行の最悪の費用」が上限を超えるなら送らない。上限を超える実行のための上書きは設けない(承認が必要) |
| 無断で繰り返し実行しない | 既定は送らない(dry-run)。送るのは `--llm run` のときだけで、1回の実行につき1リクエスト。SDK の自動再試行は切る。失敗しても自動で再実行しない(失敗した回も最悪の見積もり分を計上し続ける) |
| API 利用量と実費を記録 | 実行ごとにトークン数・推定費用(ドルと円)・所要時間・リクエスト ID を台帳に記録 |
| API キーの管理 | 環境変数 `ANTHROPIC_API_KEY` だけから読む。コード・ファイル・ログ・Git に入れない |
| 同じ実動画で無料版と比較 | `python tools/highlight_poc.py <動画> -o <出力> --llm run` で、同じ解析結果から無料版と Sonnet 版の動画を作り、`compare.md` に違いと人による比較の記入欄を出す |

- 見積もり: 素材20本・画像160枚で、入力 約3万トークン、出力の上限 1.2万トークン → 1回の最悪が約40円。500円の予算で、再実行を含めて十分に収まる。
- Claude API のキーは、環境の設定の「環境変数」にだけ置ける(サービスの仕様)。環境を使う人とセッション内のコマンドが読める点に注意。
- refusal(安全上の拒否)になった場合は、自動で別モデルに切り替えず(予算と条件の外のため)、記録して止める。
