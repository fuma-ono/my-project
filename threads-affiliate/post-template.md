# Threads投稿 構成テンプレート

`docs/marketing/2026-09-09-threads-account-repositioning.md`(2026-09-09、オーナー指示)の方針に基づく。週次→毎日Routineが投稿を生成する際はこれに従う。**2026-09-13、オーナー指示「Threads投稿戦略の再設計」により、投稿構成・投稿パターンを全面改訂した。** 経緯は`docs/marketing/2026-09-13-threads-post-hook-first-redesign.md`参照。旧版(2026-09-09改訂、悩み→気づき→商品→利用シーン→CTAの固定構成・4パターン制)はその文書に記録のみ残し、運用上は本版が優先する。

## ジャンル(2026-09-09、限定撤廃。変更なし)

特定ジャンルに絞らない。以下を幅広く対象にする:

- 生活便利グッズ・キッチン用品・家電
- スマホ・PC周辺機器・旅行用品・車用品
- 防災用品・季節商品・美容/身だしなみ用品
- 収納・掃除用品・AI/Webサービス・その他日常の「これ便利」

ただし無差別ではなく、**「誰かの困りごとを解決する便利なもの」を優先する**。

`research.py`は楽天・Amazonの商品検索APIを使うため、物販ジャンルのみ自動調査できる。AI・Webサービス系のネタは自動化の対象外で、別途手動リサーチ・執筆する。

## 基本思想(2026-09-13改訂)

**「商品を売るための投稿」ではなく、「役立つ情報・共感・意外性のあるSNSコンテンツの中に商品が自然に登場する」投稿にする。**

商品ありきで構成を埋めるのではなく、次の順番で考える:

1. 商品の特徴・利用シーン・その商品が解決する悩みを洗い出す
2. その中から「SNS上で興味を持たれるネタ」(下記9パターンのどれに当てはまるか)を選ぶ
3. そのネタを起点に投稿を書き、商品は展開の中で自然に登場させる
4. 商品の後に、押し売りにならない自然なCTAを置く

「商品説明を書いてからPR表記を付ける」という順番ではなく、「ネタを先に決めて、その中に商品を組み込む」順番で生成すること。

## 投稿パターン(9種、商品との相性で選ぶ。単純ローテーション禁止)

旧来の4パターン固定ローテーション(共感型/発見型/比較型/まとめ型)は廃止した。以下9種から、**その商品・そのネタに一番合うものを都度選ぶ**(機械的な順番送りにしない)。

| 日本語名 | `post_type`値 | 型 |
|---|---|---|
| 知らなかった事実 | `unknown_fact` | 「実はこれ、〜らしい」という意外な事実の提示 |
| あるある・共感 | `relatable` | 「これ、地味に困ってる人いない?」という共感の呼び起こし |
| 問題提起→解決 | `problem_solution` | 困りごとを掘り下げてから解決策として商品を出す |
| 比較 | `comparison` | 「AとBならどっち?」の切り口から違いを説明する |
| ランキング・厳選 | `ranking` | 「知らないと損かもな〜5選」的な切り口(リンクは代表1商品に絞る) |
| 失敗・後悔 | `failure` | 「これを知らずに損してた」「先に知っておけばよかった」という後悔ベース |
| もっと早く知りたかった | `discovery` | 「こんなのあるの知らなかった」という発見ベース |
| 議論・質問 | `debate` | 「これ派?それともこれ派?」のように読者に問いかける |
| 意外な使い方 | `use_case` | 想定外の利用シーンや使い方を提示する |

**post_typeは必ずこの9値のいずれかを`pending/*.json`に記録する。** 判断に迷う場合は、商品の特徴に一番近いものを選ぶ(例: 意外な事実が売りの商品なら`unknown_fact`、悩み解決が売りなら`problem_solution`)。

**全ての投稿にアフィリエイトリンクを含める(2026-09-09、オーナー指示。変更なし)。** `products.json`/`product-candidates.md`に該当ジャンルの実リンクがある限り、必ず紐づけて投稿する(空振りで候補が無い場合のみ、その回の生成をスキップする)。

`ranking`で複数商品に触れる場合も、リンクは代表1商品程度に絞る(リンク集のような投稿にはしない、変更なし)。

## フック生成・自己評価(2026-09-13新設)

【PR】の直後、本文冒頭の1〜2文を「フック」として最優先で作る。**この1〜2文が単なる商品紹介文になっていないか、書き終えたら必ず自己評価してから確定する:**

- 続きを読みたくなるか
- 自分ごと化できるか(「自分もそうかも」と思えるか)
- 意外性があるか
- 疑問が生まれるか
- 共感できるか

上記のいずれも満たさず、単に「〇〇という商品があります」と紹介しているだけの書き出しになっている場合は**採用せず書き直す**。

良い例:「【PR】\n\n髪乾かすの遅い人、これ知ってる?🤔」
悪い例:「【PR】\nテスコムの速乾ドライヤーを紹介します。」(いきなり商品紹介、フックが無い)

## 禁止・抑制事項(2026-09-13新設)

以下は避ける:

- 商品スペックの羅列(必ずメリットに変換する。下記の変換表を参照)
- メーカーの商品説明をそのまま言い換えただけの文章
- 冒頭から商品名・ブランド名を強く押し出す書き出し
- 「おすすめです」「便利です」だけで終わる、フックの無い投稿
- 毎回同じ文章構成・毎回同じ言い回しのCTA(「気になる人は↓」だけを毎回機械的に使わない。文脈に合わせて表現を変える)
- 過剰な広告表現・煽り文句
- 根拠のない断定的な数値効果(「〇分短縮」「〇%改善」等)。実測していない数値は書かない
- バズを狙った誇張・虚偽表現

これらは`post-template.md`の従来ルール(下記)と重複・矛盾しない範囲で追加した抑制事項であり、既存の禁止事項(医療効果の断定禁止等)を置き換えるものではない。

### スペック→メリットへの変換(必須、変更なし)

スペックをそのまま並べない。「そのスペックで何が便利になるか」に翻訳する。

| 悪い例(スペックのまま) | 良い例(メリットに変換) |
|---|---|
| 10000mAh | カイロとして使いながら、スマホの充電にも使える |
| 最高55℃・3段階温度調節 | 朝から夜まで使えて、暑くなったら温度を下げられる |

### 絵文字の使い方(2026-09-10追加、変更なし)

他の伸びているアカウントを参考に、文章の合間に絵文字を入れて読みやすくする。

- 悩み・気づきの文には🤔、共感・安心できる文には☺️や🥰など、**その一文の内容に合った絵文字**を選ぶ(意味を考えず適当に貼らない)
- 1投稿あたり**2〜4個程度**を目安にする(全ての行に付けると逆にうるさくなるため、要所だけに絞る)
- 絵文字は文章の補足として使い、絵文字だけで意味を成立させない
- **【PR】表記より前には絵文字を置かない**(`publish.py`の`validate_pr_disclosure()`が「本文の先頭10文字以内に【PR】等の表記があるか」を検証する仕組みのため、直前に絵文字を入れると表記が10文字目より後ろにずれて投稿が中断される)。【PR】の後ろの文章内で使う分には問題ない

## 商品選定基準(11項目、単純な人気順にしない。変更なし)

`research.py`のスコアは需要・満足度・価格帯の一次フィルタに過ぎない。上位候補の中から実際に書く1件を選ぶときは、以下も満たすものを優先する:

1. 日常の悩みを解決するか
2. 「知らなかった」と思わせられるか
3. Threadsで話題にしやすいか
4. 一目で便利さが伝わるか
5. 季節性があるか
6. SNSで紹介したときにクリックしたくなるか
7. 価格が購入しやすいか
8. レビュー・評価が十分か
9. アフィリエイト対象として利用可能か
10. 競合が多すぎないか
11. 投稿ネタとして継続的に展開できるか

「便利だけど知られていない」商品を優先する。

## 厳守ルール(変更なし)

- **アフィリエイトリンクを含む投稿は、本文の冒頭を必ず【PR】等の広告表示で始める**(景品表示法のステマ規制対応、省略不可)。`publish.py`が投稿時にこの表記の有無・位置を検証し、無ければ投稿を中断する
- **使ったことのない商品について「使ってみた」「効果があった」等の断定的な体験談を書かない**。「気になっている」「レビューを見ると〜という声が多い」など、事実に基づく表現に留める
- 医療・健康効果を断定しない(「絶対に眠れる」等の表現は使わない)
- **節約・お得等の便益も断定しない**。「地味にお金かからない?」のような断定調は避け、「地味に出費かさむよね」のような共感ベースの表現に留める
- スペックは全部載せず3〜4個の重要なメリットに絞る
- 1投稿1商品を基本とする(`ranking`型でもリンクは代表1商品に絞る)
- 文字数は**アフィリエイトリンクを含めて**Threadsの制限(500文字)以内(`publish.py`が投稿時に本文末尾へリンクを追記するため、`text`単体の文字数だけでなくリンクの長さも見込んで生成すること)

## 出力フォーマット(`pending/*.json`。フィールドは変更なし、`post_type`の取りうる値のみ更新)

```json
{
  "text": "本文(【PR】等の表記込みで、冒頭に配置。その直後にフック)",
  "affiliate_link": "https://... (楽天またはAmazonのアフィリエイトリンク。全投稿で必須)",
  "affiliate_platform": "rakuten|amazon",
  "product_name": "商品名(社内管理用、投稿には含めなくてよい)",
  "category": "商品ジャンル(例: キッチン用品。社内管理用、かつ下記トピックタグにもそのまま使う)",
  "post_type": "unknown_fact|relatable|problem_solution|comparison|ranking|failure|discovery|debate|use_case",
  "price": "商品価格(数値、products.jsonのpriceフィールドをそのまま転記。社内管理用)"
}
```

Amazonアソシエイトは承認済み(2026-09-09確認)。`amazon-links.md`に実際のリンクが登録されている商品はAmazon優先、未登録なら楽天を使う。

## トピックタグ(2026-09-10追加、変更なし)

Threads APIには投稿にトピックタグを1個付けられる機能(`topic_tag`パラメータ)があり、興味のある人に見つけてもらいやすくなる(インプレッション向上に有効)。1投稿につき1個・1〜50文字・`.`と`&`は使用不可という制約がある。

新たな判断ロジックを増やさないため、**`category`の値をそのままトピックタグとして使う**(`publish.py`が自動で行う。制約を満たさない`category`だった場合は黙ってスキップし、投稿自体は通常通り継続する)。投稿案生成時に`category`を書く際は、この制約(50文字以内、`.`と`&`を含めない)も意識すること。

## 計測するKPI・分析の頻度(2026-09-13、分析頻度の考え方を追記)

「いいね数」や「表示数」だけで判断しない。以下を分けて見る:

- **拡散**: views/reposts/quotes/shares
- **エンゲージメント**: likes/replies
- **アフィリエイト**: clicks(リンク単体のクリックではなく合算値である点に注意)/成約・報酬(手動突合、`docs/marketing/2026-09-09-affiliate-conversion-tracking-design.md`参照)

最終的にはアフィリエイト報酬・利益を最重視する(表示数が多い=勝ちとは判断しない)。

**30〜50投稿まで待たず、10投稿たまるごとに`analyze.py`でpost_type別の集計を確認する。** ただし1タイプあたりのサンプルが10件未満の場合は`analyze.py`が自動的に「判断不能」と明示する(`MIN_SAMPLE_FOR_JUDGEMENT`)。少数データから勝ちパターンを断定しない。

詳細と実装状況は `docs/marketing/2026-09-08-threads-post-quality-guidelines.md` 参照。`publish-log.jsonl`のスキーマは`docs/marketing/2026-09-09-threads-account-repositioning.md`参照。
