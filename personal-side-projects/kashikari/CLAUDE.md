# kashikari — 運用方針(HQ指示、2026-09-11)

kashikariは「AI App Factory」の最初の実証プロダクト。完成させること自体が目的ではなく、**「kashikariがユーザーに必要とされるプロダクトになる確率を最大化すること」**が目的。方針の全文は `docs/strategy/expectations-and-direction.md` を参照。ここには毎回のセッションで守るべき運用ルールだけをまとめる。

## 絶対原則: 指示を待たない

新機能の指示が来るまで待つことは禁止。kashikariの利用データ・フィードバック・Growthデータを見て、**「今、最大のボトルネックは何か」を自分で判断してから動く。**

判断の型:

| 観測 | 打ち手の方向 |
|---|---|
| Install多い / Activation低い | 新機能ではなく**オンボーディング改善** |
| Install少ない / Activation高い | プロダクトではなく**Growth側**の問題を疑う |
| Retention低い | 「なぜ2回目に使う理由がないか」を分析 |
| Retention高い・招待発生・オーガニック成長・収益化できている | **投資を増やす**提案をHQにする |
| 市場が小さい・Retention改善しない・Growth成立しない・収益性低い | 改善/方向転換/縮小/撤退を**選択肢としてHQに提案**する(こだわり続けない) |

## 成長ステージと見る指標

- **Stage 1(需要検証)**: Install / Activation / 初回貸し借り登録 / 初回精算 / グループ作成 / 招待 / D1・D7 Retention
- **Stage 2(PMF候補)**: 継続利用 / 招待 / グループ利用 / 再利用 / オーガニック流入 / ポジティブフィードバック。特に重要なのは「ユーザー自身が他人をkashikariに呼ぶか」(Invitation Loop)

## 判断するときに必ず考えること

「競合がいるから難しい」で終わらせない。市場の問題・ユーザーの不満・競合との差・kashikariの強み/弱み・Growthとの相性・収益化可能性・技術コストを踏まえて、**成功確率を上げるには何をすべきかまで提案する。**

## 拡張の順番(需要が確認された領域のみ)

貸し借り → 立替 → 割り勘 → グループ精算 → 旅行会計 → サークル会計 → 継続的なグループのお金管理。全部を先回りして実装しない。

## 現状(このファイル更新時点。詳細は `mobile/README.md` の最新エントリを参照)

- 開発: 主要機能(精算2段階確認・自動精算・割り勘・招待・催促・課金/広告・会計レポート・サークル会計・Sentry・フィードバック機能)は実装済み
- ローンチ: App Store審査に提出済み、結果待ち。Android は Play Console のデベロッパー確認(実機ログイン必須)待ちで保留
- 計測: `analytics_events`(グループ作成・招待発行・招待クリック・参加完了・精算完了)、`feedback`(自由記述、本人含め非公開)は実装済み。**Stage 1指標(Install/Activation/D1・D7 Retention)をまとめて見るダッシュボード・定期集計の仕組みはまだ無い** — ローンチ後、最初に着手すべき運用課題
- 週次トリアージの自動化(フィードバック監視→バグ修正/Issue化/週次サマリー)は設計済みだが、**Supabase service role keyがこの開発環境に未登録のため未稼働**
- 現段階はまだ「Stage 1: 需要検証」のデータが取得できていない(未ローンチ)。ローンチ前に新機能を追加提案することは、この方針と矛盾するため避ける
